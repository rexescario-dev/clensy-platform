# apps/web

The Clensy dashboard/site: Next.js (App Router) + TypeScript + Tailwind CSS, consuming `@clensy/ui` and `@clensy/client` against `apps/api`'s GraphQL endpoint.

Full application shell (sidebar/header/user menu/logout) mounted once for every route under `/app/*`. `/login` is the public sign-in page. `/app` itself is a role-aware landing ([#89 plan](../../docs/superpowers/plans/2026-10-01-tenant-aware-application-shell-plan.md) decision 5): a Super Admin goes to the `/app/platform` placeholder (platform administration is deferred), tenant users to their first visible nav item. A user whose session is invalid is sent to `/login` from any `/app` page by the one `SessionGuard` in `app/app/layout.tsx` ([#131 spec](../../docs/superpowers/specs/2026-10-07-session-routing-design.md)). It acts only on positive evidence: an `UNAUTHENTICATED` API response, or a `network-only` `currentAdmin` check on each pathname change that finds no principal. So an API outage shows the page's own error instead of signing the user out, and the landing shows "Unable to load your account.". The sidebar shows only the nav items whose API read gate includes the user's role (`viewRoles` in `lib/nav-groups.ts`, scope first — a Super Admin gets no tenant nav), and the user menu shows the role label and an "Organization account" / "Platform account" scope line. Typing or bookmarking the URL of a page hidden from the user (by role, or by scope: a Super Admin on a tenant page, a tenant user on `/app/platform`) shows a shared "This page isn't available to you." state with a link to their landing page instead of the page. The message is that page's `<h1>`, so screen-reader heading navigation reaches it ([#132](https://github.com/rexescario-dev/clensy-platform/issues/132)). Its home link is a `@clensy/ui` `Button` link (`asChild`, `variant="link"`) rendered onto the `next/link` `Link`, the convention for standalone navigation actions in shell chrome ([#134](https://github.com/rexescario-dev/clensy-platform/issues/134)). The same gate owns the document title: every `/app` page is titled from its nav label (`Services · Clensy`), the unavailable state is `Page unavailable · Clensy`, and `/app` itself is `Clensy`. The format lives in the `nav.documentTitle` messages, the root layout sets no title, and `/login` keeps `Clensy` through `app/login/layout.tsx` ([#143 spec](../../docs/superpowers/specs/2026-10-08-app-document-titles-design.md)). This comes from the one `PageVisibilityGate` in `app/app/layout.tsx`, which uses `isGatedPath`/`canViewPath` in `lib/nav-groups.ts`, the same `viewRoles` rules as the sidebar ([#114 spec](../../docs/superpowers/specs/2026-10-04-role-aware-typed-urls-design.md)). `/app` and unlisted paths are not gated, and the gate never redirects. Nav visibility, the gate, the landing and the platform page are UX only; the API remains the authorization boundary. The four migrated modules are `/app/admin` (staff/roles for the Tenant Owner's own tenant, Tenant-Owner-only), `/app/customers`, `/app/cleaners` + `/app/cleaners/teams`, and `/app/catalog` + `/app/catalog/add-ons` (Admin, Customers, Cleaners/Teams, Catalog/Add-ons), all built on shared `@clensy/ui` primitives (data table, detail drawer, form dialog, confirmation dialog, feedback states).

- `docker compose up -d --build` (from the repo root) — runs this app on port 3001 (matches `apps/api`'s `WEB_ORIGIN` CORS default) alongside `apps/api` and Postgres. See [local development](../../docs/getting-started/local-development.md).
- `pnpm --filter web start:dev` — Next.js dev server on port 3001, for working on the web app against a running API.
- `pnpm --filter web test` — Vitest, including the guard tests described below.
- `pnpm --filter web build` — production build.
- See `.env.example` for the `NEXT_PUBLIC_API_URL` env var consumed by `@clensy/client`.

## UI

`apps/web` consumes UI only through [`@clensy/ui`](../../packages/ui/README.md)'s public API:

- `apps/web` MUST NOT contain shadcn-generated components.
- `apps/web` MUST NOT import shadcn or `radix-ui` components directly.
- `apps/web` MUST NOT depend on shadcn-specific configuration (no `components.json`).

`apps/web` does still keep `cn` and `lucide-react` as ordinary dependencies for its own non-primitive needs (its own `className` composition, its own icons) — that isn't an exception to the rule above, since neither is a shadcn-specific dependency.

`apps/web` also consumes reusable Clensy domain components (e.g. `LoginForm`, `BookingDataTable`, `LaundryOrderDataTable`, `LaundryOrderProgress`, `LaundryCustomerPicker`, `LaundrySearchCombobox`, `LaundryFulfillmentFieldset`, `StaffDataTable`, `CreateStaffForm`) through [`@clensy/web`](../../packages/web/README.md)'s public API. Unlike `@clensy/ui`, these are self-translating — they own their own UI copy via `@clensy/web`'s own i18n context, not via translated-strings-as-props from `apps/web`.

`apps/web` also still depends on the `shadcn` package itself, and `app/globals.css` still has `@import "shadcn/tailwind.css"`. This is not an exception to the rule above either: it's a CSS token dependency, not a component dependency. `apps/web/app/globals.css` owns the base theme-token layer that `@clensy/ui`'s primitives consume by class name (see the design spec §4.7), and that CSS import is the only reason the `shadcn` package stays in `apps/web/package.json`. Do not remove it — doing so breaks the Tailwind build.

## Laundry list (`/app/laundry`)

The laundry order list ([#163](https://github.com/rexescario-dev/clensy-platform/issues/163); [plan](../../docs/superpowers/plans/2026-10-10-laundry-order-list-plan.md); [lifecycle spec](../../docs/superpowers/specs/2026-09-06-laundry-orders-lifecycle-design.md) Amendment #164 §8.4.4) filters, sorts and pages on the server:
- **Search:** customer name (escaped `iLike`), plus an exact match on a full order UUID.
- **Filters:** status and fulfillment, each with `eq`.
- **Sort:** an allowed field, then `id ASC`.
- **Paging:** 20 per page.

**URL state.** The list keeps its state in the URL, in `q`, `status`, `fulfillment`, `sortBy`, `sortOrder` and `offset` (`lib/use-laundry-order-list-url-state.ts`). Parsing validates every value. The offset must be plain decimal digits within GraphQL's `Int` range, or it is malformed ([#171](https://github.com/rexescario-dev/clensy-platform/issues/171)); it is snapped to a page boundary. Variables are built in `lib/laundry-order-list-query.ts`. The search box debounces for 300 ms (`lib/use-laundry-search-draft.ts`).

**Native history writes.** Unlike the bookings list's `router.replace`, this list writes its URL with the native History API, which Next.js syncs into `useSearchParams`. Each write builds on the live `window.location`, keeping the hash and every param the list does not own.
- **List updates** use `replaceState`, so they add no history entry.
- **Opening the drawer** uses `pushState`, from a row or after creating an order. The pushed entry carries the drawer marker in `history.state` (see Drawer hook).
- **Closing the drawer** goes Back (`router.back()`) when the current entry carries the marker, so also after Forward or a refresh. A drawer reached by a direct link has no marker, so it closes with `replaceState`, with `detail` removed.
- **List updates made while a drawer is open** keep the marker.
- **Back/Forward** cancels a search still waiting to commit.

The page makes no `router.push` or `router.replace` of its own.

**Drawer hook.** `lib/use-detail-drawer.ts` serves every drawer page. It has two laundry-only methods, `openWithHref(href)` and `closeWithHref(href)`, beside `open` and `close`.
- **Opening** pushes the drawer entry natively, with a marker in `history.state` (`__clensyDetailDrawer: <param>`). Next.js keeps that marker across Back, Forward and refresh ([#173](https://github.com/rexescario-dev/clensy-platform/issues/173)).
- **Closing** goes Back when the current entry carries the marker for its param. Otherwise it replaces the entry, so a direct link never leaves the app. A second close before that Back lands (× and the backdrop together, a double Escape) is ignored, so it never goes Back past the list.
- **`close` takes no argument.** The other pages pass it straight to `onClose`, which `DetailDrawer`'s × button calls with a click event. `lib/use-detail-drawer.test.tsx` pins that.
- **No `router.refresh()` or server actions near a drawer.** Next.js drops the marker when it rewrites the entry for either, and × would then replace the entry again. `lib/use-detail-drawer.guard.test.ts` fails if either appears in `apps/web`, `packages/web/src` or `packages/ui/src`. Its known limits are listed in the [#173 plan](../../docs/superpowers/plans/2026-10-11-drawer-history-entry-marker-plan.md).

Until [#161](https://github.com/rexescario-dev/clensy-platform/issues/161), a row opens the drawer (`?detail=<id>`), not `/app/laundry/[id]`.

## Laundry intake (`/app/laundry`)

"+ New Laundry Order" opens `components/laundry/create-laundry-order-dialog.tsx` ([#160](https://github.com/rexescario-dev/clensy-platform/issues/160); [plan](../../docs/superpowers/plans/2026-10-13-laundry-intake-modal-plan.md); [lifecycle spec](../../docs/superpowers/specs/2026-09-06-laundry-orders-lifecycle-design.md) Amendment #164 §8.4.4). It is a `FormDialog` with `@clensy/web`'s `LaundryCustomerPicker` and `LaundryFulfillmentFieldset`, and it calls the existing `receiveLaundryOrder`.
- **Customer search** (`lib/use-laundry-customer-search.ts`): the trimmed text is searched on the server after 300 ms, as `fullName` `iLike` (escaped like the list's search), 20 per search, by name then id. An empty input sends no query. While the searched text differs from the input, or the query is loading, the hook returns `loading` with no options, so an older text's results are never offered. `truncated` drives "More customers match…": narrowing the text is the way past 20 matches; there is no load-more.
- **Form:** `react-hook-form` with `clensyResolver` ("Select a customer."). Any edit after choosing clears the chosen id. Server field errors (`normalizeApiValidationErrors`) show on their field, which is marked invalid and described by the error, and clear when it changes. Focus then moves to the first field with an error in form order (customer, then fulfillment), so a screen reader reads that field and its error once; field errors carry no live role ([#181](https://github.com/rexescario-dev/clensy-platform/issues/181)). Anything else shows "Unable to create laundry order." as a `role="alert"` in the dialog, with the fields kept. A success response without an order id shows "The order may have been created. Check the laundry list before trying again." and is not retried.
- **One mutation per submit:** a synchronous guard is taken before validation and released when the attempt settles, so two submits fired in one turn send one mutation and a failed attempt can be retried.
- **Reset:** the page gives the dialog a new React `key` on every opening.
- **Roles:** the button shows for `canReceiveLaundryOrder`. The "Add a customer" link to `/app/customers` shows only when `canViewPath` allows it; there is no inline customer form.
- **Success:** the page closes the dialog, toasts "Laundry order created.", and opens the drawer on the returned id at once with `openWithHref`; the list refresh runs behind it and is not awaited. Until #161, a successful create opens the drawer, not `/app/laundry/[id]`.

## Laundry order page (`/app/laundry/[id]`)

`app/app/laundry/[id]/page.tsx` is the focused page for one order ([#156](https://github.com/rexescario-dev/clensy-platform/issues/156); [plan](../../docs/superpowers/plans/2026-10-14-laundry-order-page-plan.md); [lifecycle spec](../../docs/superpowers/specs/2026-09-06-laundry-orders-lifecycle-design.md) Amendment #164 §8.4.4). It is a client page that reads `id` with `useParams` and keys its content by `id`.
- **Layout:** back link to `/app/laundry`, `PageHeader` (customer as the only `h1`, order id, status badge and fulfillment), `LaundryOrderProgress`, a four-card summary `dl`, an in-page section nav (`nav aria-label="Order sections"`, plain `#laundry-order-<section>` anchors), and six sections: Overview (a one-line pointer to Price once lines exist), Weighing, Services, Price, Invoice, Actions.
- **Read-only, except Weighing, Services and Price:** outside those three sections the page renders no button, form or mutation. Invoice shows the facts the order already records; Actions names the lifecycle verbs the role may take as text. #166 and #165 replace those bodies with controls.
- **Weighing ([#155](https://github.com/rexescario-dev/clensy-platform/issues/155); [plan](../../docs/superpowers/plans/2026-10-14-multi-entry-laundry-weighing-plan.md); spec Amendment #164 §8.4.1, §8.4.4):** `WeighingBody` picks one of three views with `laundryWeighingView(status, verbs)` (`lib/laundry-order-page.ts`).
  - **Editor:** when `laundryOrderActions` offers `weigh` (`RECEIVED`/`WEIGHED` for OWNER, OPS_MANAGER and SCHEDULER), `components/laundry/laundry-weighing-editor.tsx` lets staff enter one row per bag, basket or batch in kilograms and shows a live combined total. `lib/laundry-weight-entries.ts` parses each row into whole grams by splitting on `.`, never by multiplying a float. It accepts at most 3 decimals and caps each row and the total at the GraphQL `Int` maximum. One `weighLaundryOrder` sends the sum. Controls stay disabled until the save and the order refetch settle, and then focus returns to Record weight unless the user has moved it outside the form. `onPendingChange` tells the page when a save starts and when it ends, so Price holds Confirm meanwhile (#162). While a price is being confirmed, the editor is `disabled` and drops a submit. A submit blocked by an invalid row focuses the first such row; a failure keeps the rows and shows the server message (`lib/graphql-error-message.ts`) or a fallback. A recorded weight prefills one row for re-weighing.
  - **Locked:** a status in the explicit `LAUNDRY_PRICED_STATUSES` set shows "Weight is locked because this order has been priced." and the weight, to every role. `CANCELLED` and `REJECTED` are not in the set, even when cancelled after pricing.
  - **Read-only:** any other case shows the recorded weight or "Not weighed yet." The server stays authoritative: `weighLaundryOrder` rejects `0` (`@Min(1)` and the service check), and the database CHECK stays `>= 0`, so stored `0` rows remain.
- **Services ([#158](https://github.com/rexescario-dev/clensy-platform/issues/158); [plan](../../docs/superpowers/plans/2026-10-15-laundry-services-selection-plan.md); spec Amendment #164 §8.4.2–§8.4.5, §4.5 step 3a):** `ServicesBody` picks one of five views with `laundryServicesView({ hasTotal, roleResolved, status, verbs })` (`lib/laundry-service-selection.ts`). Services chooses services and counts only; every unit, rate and amount is in Price (#162).
  - **Editor:** a `WEIGHED` order whose role may price (`laundryOrderActions` offers `price`) shows `components/laundry/laundry-services-editor.tsx`: a base service and any number of add-on rows, each a `LaundrySearchCombobox`.
    - **Search:** a picker browses the first 20 active entries when focused, then searches by a debounced (300 ms) `name.iLike` filter; the server does all filtering (`lib/use-laundry-catalog-search.ts`). "Showing the first 20. Type to narrow." appears when more match.
    - **Count:** the unit comes only from `previewLaundryOrderPrice`, requested after a 300 ms debounce. The count input shows only for a line whose unit the server last reported as `PER_ITEM`, and a count is sent only for such a line. Returning within one debounce to an input whose result has already settled sends no new request and keeps that result.
    - **Stale responses:** the hook (`lib/use-laundry-service-selection.ts`) keys each request by `[weightGrams, input]`; a response for another key, or one whose lines do not match the input by position, kind and id, is ignored.
    - **Missing price:** when the server's message exactly matches `No effective price for serviceId|addOnId <uuid>` for a selected line, the editor shows an alert naming that line and marks its row. Any other failure shows the server text or "Couldn’t preview the price."
    - **Duplicate add-on:** blocked in the UI only (the server allows repeats, §8.4.3). The message shows only while another row still holds the add-on.
    - **Accessibility:** the base service and each add-on row are `role="group"` with an `aria-label`.
  - **Shared state:** `PricingSections` calls `useLaundryServiceSelection` above Services and Price, keyed by order id, so Price reads `ready`, `complete`, `previewLoading`, `priceInput`, `preview` and `previewError`, calls `retryPreview`, and starts no preview of its own. While a price is being confirmed, the editor is `disabled`.
  - **Hidden:** a `WEIGHED` order while the role is still loading renders nothing, so read-only copy never flashes before the editor.
  - **None:** a `WEIGHED` order the role may not price, or any status other than `RECEIVED` with no total, shows "No services selected yet."
  - **Before weighing:** `RECEIVED` shows "Weigh the order before choosing services."
  - **Locked:** any order with a total shows "Services are locked because this order has been priced.", whatever its status. A total is written only by `priceLaundryOrder`, and the same signal selects Price's Final card, so the two sections never disagree.
- **Price ([#162](https://github.com/rexescario-dev/clensy-platform/issues/162); [plan](../../docs/superpowers/plans/2026-10-15-laundry-price-review-plan.md); spec Amendment #164 §8.4.2, §8.4.4, §8.4.5):** `PriceBody` picks a view with `laundryPriceView({ hasTotal, roleResolved, status, verbs })` (`lib/laundry-price-review.ts`), in this order: a total shows **Final price**, for any status and role and while the role loads; any other status than `RECEIVED` or `WEIGHED` shows "This order was not priced."; a loading role shows nothing; a `WEIGHED` order whose role may price shows the **Estimate** card; otherwise "Price is available after the order is weighed and services are chosen."
  - **Card:** `components/laundry/laundry-price-card.tsx`. Each row is a `grid-cols-[minmax(0,1fr)_auto]` grid with `tabular-nums`: the name, quantity and rate phrase on the left, the amount on the right, and a minimum-charge note under it ("Minimum charge applied (₱…)." or, with no server minimum, "Minimum charge applied."). Every figure comes from the preview or the snapshot; the client computes none.
  - **Estimate states** (`laundryEstimateState`): "Select a base service to see an estimate.", "Finish choosing services to see an estimate.", "Updating estimate…" (`aria-live="polite"`), "Couldn’t calculate the estimate." with **Try again** (a new request for the same input), or the breakdown with "Estimated total". Only the ready state shows rows and enables Confirm. A weight being saved and reloaded counts as loading. The confirm caption shows in every state.
  - **Confirm:** `lib/use-confirm-laundry-price.ts` sends the previewed `priceInput` unchanged to `priceLaundryOrder`, once: a ref taken synchronously drops a second click. The button reads "Confirming…" and both editors stay disabled through the mutation and the refetch. Success toasts "Price confirmed."; a failure shows the server message or "Unable to price order." in an alert, keeps the selection, and clears on the next edit. A failed refetch leaves the page error state. No invoice or payment mutation is called, and there is no reprice.
  - **Final price:** the frozen `pricingSnapshot` rows (their `description`) and `totalMinorUnits`, under "Order total", with no button.
- **Data:** `laundryOrder(id)` (`LaundryOrderDetail`, `network-only`) and `InvoiceForOrder`. An id that is not UUID-shaped (`isUuid` in `lib/laundry-order-list-query.ts`) skips both queries and shows the not-found state. The fragment requests `lines(paging: { limit: 100 })`, so the drawer and the laundry mutations get up to 100 lines too; "More lines are not loaded." shows in Price's Final card when `hasNextPage` is true.
- **Query states:** while the order query loads, the page shows `LoadingState`, even if Apollo still holds an earlier order; an error or a `null` order shows "Unable to load laundry order." The invoice result goes through `resolvedInvoiceNodes` (`lib/laundry-order-page.ts`): only a finished, error-free result with an `invoices.nodes` array counts, and the nav and the Invoice section read that one value. Loading, failed and incomplete results stay unresolved, never "No invoice yet."
- **Current section:** `currentLaundryOrderSection` marks the next step forward from `laundryOrderActions`: Weighing for `RECEIVED`, Services when pricing is offered, Invoice when one can be generated and none exists, otherwise Actions; none when the role has nothing to do or is still loading.
- **Cutover helpers:** `laundryOrderHref(id)` and `laundryDetailRedirectHref(search)` are tested but not wired; [#161](https://github.com/rexescario-dev/clensy-platform/issues/161) uses them to send rows, post-create navigation and `?detail=` links here and to remove the drawer.

## i18n

`next-intl` is wired for a single locale, `en` (see [the design spec](../../docs/superpowers/specs/2026-09-13-web-i18n-architecture-design.md) for the full architecture). No second language ships yet, and no locale-prefixed routing exists — this is about getting product copy behind translation keys, not about shipping translations.

**Catalogs** live at `apps/web/messages/en/*.json`, one file per namespace. Current namespaces: `common` (empty for now), `nav` (sidebar, plus the shell's `userMenu`, `landing`, `platform` and `unavailable` copy), `validation`. Role labels are not here: they come from `@clensy/web`'s shared `roles` namespace. `apps/web/i18n/messages.ts` merges them; `apps/web/i18n/request.ts` is the next-intl plugin/runtime entry point that resolves the locale (always `en`) and calls it. (An `auth` namespace previously lived here for `LoginForm`'s copy — retired once `LoginForm` became self-translating via `@clensy/web`'s own i18n context; see [the LoginForm self-translating spec](../../docs/superpowers/specs/2026-09-20-login-form-self-translating-design.md).)

**`@clensy/web` copy and app-wide overrides.** `@clensy/web`'s components translate their own copy. Every route under `/app/*` resolves that copy through one **app i18n boundary**: `AppI18nProvider` (`components/layout/app-i18n-provider.tsx`), which `app/app/layout.tsx` mounts around `DashboardLayout` ([single app i18n provider spec](../../docs/superpowers/specs/2026-10-02-single-app-i18n-provider-design.md), #115).
- **Locale:** comes from next-intl's `useLocale()`.
- **Overrides:** come from exactly two layers ([tenant label overrides spec](../../docs/superpowers/specs/2026-10-03-tenant-label-overrides-design.md), #118):
  - the static app layer, `APP_I18N_OVERRIDES` in `lib/clensy-i18n-overrides.ts`, typed `DeepPartial<ClensyMessages>` and committed as `{}`;
  - the tenant layer, `currentAdmin.tenantLabelOverrides` (the signed-in tenant's ops-seeded role labels, validated by the API), mapped by `lib/tenant-label-overrides.ts`. It applies only when its `locale` matches next-intl's locale, and it is empty while `currentAdmin` has no data.

  `AppI18nProvider` passes `deepMerge(APP_I18N_OVERRIDES, tenantLayer)`, so the precedence is tenant label > static override > package default. It reads the default cache-first `useCurrentAdminQuery()` and never blocks rendering. Login and logout clear the Apollo store after confirming the session change and before navigating, so one tenant's labels never reach the next session.
- **No local providers:** a page or component that renders `@clensy/web` components relies on this boundary and MUST NOT mount its own `ClensyI18nProvider`. `lib/web-shell-regressions.test.ts` fails if a second mount appears in any scanned source file (`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.mts`, `.cts`). It also fails on any **provider escape** (#117): a re-export of `ClensyI18nProvider` from `@clensy/web` (including `export *`), or any use of the imported provider other than as a JSX tag or in `typeof`. So a barrel, an alias or `createElement` can't be used to mount it under another name. Loading the package with `require('@clensy/web')` or `import('@clensy/web')`, or with a non-literal `require`/`import()`, is an escape too (#120). Type-only positions that cannot mount it are not escapes: `typeof P.x`, a namespace in `implements` or interface `extends`, and same-spelled declaration names such as members, enum members and labels. Class `extends` and every value use still are (#124).
- **Public entry point only:** `apps/web` imports `@clensy/web` through the bare `'@clensy/web'` specifier. The same test fails on any deep `@clensy/web/…` specifier, or any relative, absolute or `@/` path into `packages/web`, in any import, export, `require`, `import()` or type-only form (#120). A path through a `node_modules/@clensy/web` link (pnpm's symlink to `packages/web`), or anything beneath it, fails too (#122).
- **One dashboard shell:** `DashboardLayout` is rendered exactly once, in `app/app/layout.tsx`, as the boundary's direct child. Rendering it anywhere else fails the test (#120).
- These checks are syntactic. They read import specifiers as written and do not resolve modules.
- **`/login`** stays outside the boundary and uses `@clensy/web`'s package defaults.

**Adding a key:** add it to the right namespace's JSON file (or a new namespace file, if you also add it to `i18n/messages.ts`'s merge), then consume it:

```tsx
'use client';
import { useTranslations } from 'next-intl';

const t = useTranslations('nav');
t('sidebar.primary'); // -> the string at messages/en/nav.json's "sidebar.primary" key
```

A server component uses `getTranslations` (`next-intl/server`) against the same catalogs instead.

**Rules, enforced by lint (`apps/web/eslint.config.mjs`) where possible:**

- Never `import` a `messages/**` catalog file, or `i18n/messages`, directly outside `apps/web/i18n/` — always go through `useTranslations`/`getTranslations`.
- `@clensy/ui` MUST NOT import `next-intl` or hold a Clensy message catalog. It takes already-translated strings (`label`, `error`, `title`, …) as props; `apps/web` translates, `@clensy/ui` renders.
- A translation key is a stable identifier, not derived from its current English text — renaming the visible copy doesn't require renaming the key.

**Documented but not yet implemented** (see the design spec §4.5–§4.6 for the full rationale):

- `@clensy/validation` (#51, [package README](../../packages/validation/README.md)) now exists and is wired into the Add Customer form, but it ships fixed English messages today — it does not import `next-intl` or produce ICU keys. Rendering its rule/field structure via `t('validation.<rule>', { field })` against `messages/en/validation.json`'s ICU templates remains a future integration (its own [design spec](../../docs/superpowers/specs/2026-09-15-clensy-validation-design.md) §6), not something #51 implemented either.
- `normalizeApiError`: `API error → stable error metadata when available → rule key → validation.<rule>`, falling back to a generic `common.errors.requestFailed` key that doesn't exist in the catalog yet (no caller needs it today). `@clensy/validation`'s own `normalizeApiValidationErrors` (#51) solves a narrower, related problem — mapping a failed GraphQL mutation onto its `FieldErrors` contract directly, not onto this catalog's `validation.<rule>` keys.
