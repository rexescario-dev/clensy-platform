Where this plan and the Accepted specification disagree, the specification wins and this plan must be revised.

## 1. Delivery intent

Implement exactly what the Accepted specification authorizes: migrate `modules/bookings` off its fake `customerName`/`serviceType` strings onto real `customerId`/`propertyId`/`serviceId`/`teamId` references validated against `modules/customers`, `modules/catalog`, and `modules/cleaners`' existing application-layer read contracts (spec §4.1, §4.2); add a `pricingSnapshot` value object captured at creation time (spec §4.1); bring the GraphQL surface to RBAC/audit parity with every other Phase-1 module (spec §4.3, §4.4); update REST's DTOs/response body in lockstep with the one shared command the two transports have always mapped into, while leaving REST's routes, envelope, and pre-existing absence of auth/audit untouched (spec §4.4, §5); rewrite the legacy seed data to the new schema (spec §4.1 addendum); and ship `/app/bookings` on the Dashboard UX Foundation shell (spec §4.6). Not a redesign of any of it — every behavioral decision below traces to the Accepted spec or is called out explicitly as an M4 implementation choice the spec deliberately left open (§3).

## 2. Constraints (SHALL / SHALL NOT)

**SHALL** (traced to spec section):
- `Booking` domain object holds `customerId`, `propertyId`, `serviceId` (all required, immutable after creation), `teamId` (nullable, mutable), `scheduledAt`, `status`, `pricingSnapshot: BookingPricingSnapshot`, `createdAt` — no `customerName`/`serviceType`, no `updatedAt` (§4.1).
- `BookingPricingSnapshot` holds `priceMinorUnits` only — no other service fields snapshotted (§4.1).
- `customerId`/`propertyId`/`serviceId`/`teamId` carry no TypeORM relation decorator; each is a plain `@Column` with the FK constraint hand-added in the migration's raw SQL (§4.1). All four FKs are `ON DELETE RESTRICT` (§4.1).
- `pricingSnapshot` is persisted as a TypeORM embedded column (`@Column(() => BookingPricingSnapshot)`), not a second table (§4.1).
- `BookingsService.create`, within one transaction: resolve/validate `customerId` → `propertyId` (and its `customerId` match) → `serviceId` (and `active`) → active `PricingRule` for `serviceId` → `teamId` if provided, in that order; insert with `status: PENDING` and the resolved `pricingSnapshot` (§4.2).
- `BookingsService.update` accepts only `scheduledAt`, `status`, `teamId` — `customerId`/`propertyId`/`serviceId` are not fields of `UpdateBookingCommand`/`UpdateBookingInput`/`UpdateBookingDto` at all (§4.2). `UpdateBookingInput`/`UpdateBookingDto` are their own explicit shapes, **not** `PartialType(Create...)` (§4.2).
- `teamId` on update: omitted retains current value; explicit `null` clears it; a non-null value is re-validated via `TeamsService.getTeam` before being set (§4.2).
- Exception types/triggers exactly as spec §4.2/§4.7 state: `NotFoundException` for missing `customerId`/`propertyId`/`serviceId`/`teamId`/booking `id`; `BadRequestException` for property-doesn't-belong-to-customer, inactive service, service-with-no-active-price.
- Every GraphQL operation requires `AuthGuard`; write ops (`createBooking`/`updateBooking`/`removeBooking`) require `Role.OWNER`/`OPS_MANAGER`/`SCHEDULER`/`CUSTOMER_SUPPORT`; read ops (`booking`/`bookings`) require any of all six roles (§4.3).
- Every GraphQL mutation logs exactly one audit event in the same transaction as its state change: `booking.create`/`booking.update`/`booking.remove`, `entityType: 'booking'` (§4.4). Read operations are not audited. `removeBooking` gains audit logging that did not exist before this slice — its hard-delete semantics are otherwise unchanged.
- REST (`booking.controller.ts`) gains no `AuthGuard`/`@Roles()`/audit on any endpoint — reads and mutations alike (§4.4, §5). REST DTOs' field names, and consequently REST response bodies, change to the new `customerId`/`propertyId`/`serviceId`/`teamId`/`pricingSnapshot` shape because there is no separate REST view-model layer (§5) — routes, HTTP verbs, and the response envelope (status codes, error format) are otherwise unchanged.
- `BookingType` (GraphQL) exposes `customer`, `property`, `service`, `team` as computed fields resolved via a batching-capable read path — no one-query-per-parent-row over a `bookings` list (§4.5). `pricingSnapshot` is a direct (non-computed) nested field.
- `apps/web`'s create-booking flow uses cascading selects (customer → property → service → team) inside one `FormDialog`, not a multi-step wizard; the property select is populated via the existing `customerProperties(customerId)` query (§4.6, §2).
- The web UI's destructive action is labeled and worded as "Delete booking" (`removeBooking`), visually/terminologically distinct from the non-destructive `status: CANCELLED` transition (§3, §4.6).
- `BookingStatus`'s four values and `updateBooking`'s transition-free semantics are unchanged (§2).
- `apps/web/middleware.ts` requires no edit — its existing `/app/:path*` matcher already covers `/app/bookings` (§4.6).
- Tests: unit coverage for the validation chain; a create-booking e2e golden path naming active pricing as a required step, not just "service"; a dedicated pricing-snapshot-immutability e2e; immutable-FK-vs-mutable-`teamId` assertions (§2, §6 — M3 round 2 additions).

**SHALL NOT** (explicit spec/design non-goals — do not invent):
- No availability/conflict checking (§2).
- No re-snapshotting or recalculating `pricingSnapshot` after creation (§2).
- No relationship to `modules/jobs`/`modules/quality` (§2).
- No `assignBookingTeam` mutation — `teamId` stays a plain `Create`/`UpdateBookingInput` field (§2, §5).
- No new `packages/ui` primitive, no multi-step wizard component (§2, §5).
- No cascading-delete handling beyond the stated `RESTRICT` FKs (§2).
- No currency/multi-currency changes (§2).
- No `AuthGuard`/RBAC/audit added to REST (§2, §4.4, §5).
- No redesign of any Accepted upstream spec's contracts (Admin Foundation, Customers & Properties, Cleaners & Teams, Catalog, Dashboard UX Foundation) (§7).

## 3. Implementation decisions (M4 choices)

The specification leaves these implementation details open; this plan fixes them for M6 execution so no implementer has to choose alone:

- **Cross-module validation reads happen *before* `BookingsService.create`/`.update` open their own transaction, not inside it — this resolves a genuine internal tension in spec §4.2's own wording, not an unambiguous instruction this plan overrides.** §4.2 contains two adjacent statements that do not literally agree: its opening paragraph defines the transaction boundary narrowly — "the entity write **and the corresponding `AuditLogger.log()` call** execute within one database transaction" (naming exactly two things) — while the `create` bullet immediately below opens with "within one transaction, in order," then lists all six steps including the five cross-module reads. Read hyper-literally, the second sentence would require `CustomersService.getCustomer`/`PropertiesService.getProperty`/`ServicesService.getService`/`PricingRulesService.getActivePricing`/`TeamsService.getTeam` to share `BookingsService`'s own `EntityManager` — but that is not achievable without changing those methods' signatures across three other modules' own Accepted specs (each is a plain-repository read with no `EntityManager` parameter, confirmed against the live code: `getCustomer(id) { return this.customerRepository.findOneBy({ id }); }`, identically for `getProperty`/`getService`/`getTeam`), which is out of scope for this plan to do and would itself be a larger, unauthorized redesign of upstream Accepted contracts. Nor does any existing module in this codebase do this: not even `PropertiesService.create`'s own `customerId` check joins a cross-*module* transaction — it works only because `CustomerEntity` and `PropertyEntity` share one module's manager, which is exactly the case Bookings is not in (spec §2.6 forbids `BookingsService` from reaching into another module's entity/repository directly, which is the only way it could otherwise join that manager). Given the structural impossibility of the literal reading, this plan takes the paragraph's narrower, more precise definition as authoritative and reads "within one transaction, in order" as describing the ordered sequence that constitutes one coherent `create()` call, not a literal single-`EntityManager` requirement over all six steps. This resolution is also observably behavior-preserving: the five reads are side-effect-free, so whether a failing read is "inside" a transaction that then rolls back or simply never reaches the transaction at all produces an identical outcome (nothing written) — there is no product-visible difference between the two readings, which is precisely the class of question design review treats as an implementation mechanism, not normative product semantics (M4 prompt §7). The five validation calls run as ordinary sequential `await`s ahead of `this.dataSource.transaction(...)` (sequential, not `Promise.all`, matching the spec's own enumerated ordering literally); only the `BookingEntity` insert/update and its audit event are inside the transaction, mirroring every other module's `create`/`update` shape exactly. **Formal invariant this decision relies on, stated explicitly rather than left implicit:** none of `Customer`/`Property`/`Service`/`Team` has a delete operation anywhere in Phase 1 (spec §4.1), so there is no window in which a reference validated by a pre-transaction read could be invalidated before the subsequent write — if a future slice ever adds a delete operation to any of those four, this invariant (and this plan's transaction-boundary choice) must be revisited.
- **`BookingType` exposes no raw `customerId`/`propertyId`/`serviceId`/`teamId` GraphQL fields — only the four computed relation objects (`customer`, `property`, `service`, `team`).** Mirrors `CleanerType`'s precedent exactly (`cleaner.type.ts`: "Deliberately no `@Field()` for `teamId`"): GraphQL schema exposure is controlled entirely by `@Field()` decorators, so a client reads `booking.team.id`, never a separate `booking.teamId`. `apps/web`'s edit form reads/writes IDs via the resolved objects (`booking.team?.id`), the same pattern `apps/web/app/app/cleaners/page.tsx` already uses for `cleaner.team?.id`.
- **Three new bulk read methods, one per owning module that doesn't already have one** — `CustomersService.getCustomersByIds(ids)`, `PropertiesService.getPropertiesByIds(ids)`, `ServicesService.getServicesByIds(ids)` — added in Task 1, additive-only, identical shape and rationale to the already-existing `TeamsService.getTeamsByIds`/`PricingRulesService.getActivePricingForServiceIds`. Each returns exactly the rows found for the given ids (repository `findBy({ id: In(ids) })`), no synthetic `null` entries — gap-filling is the loader's job (spec §4.5's M3-round-2 clarification: additive to the owning module's contract, not a modification of the existing singular method).
- **`BookingRelationLoaders`, a new request-scoped provider owned by `modules/bookings`** (`presentation/graphql/booking-relation.loaders.ts`), not a reuse of `CleanerTeamLoaders` — `CleanerTeamLoaders` is owned by, and not exported from, `CleanersModule` (its module `exports` list is `[TeamsService, CleanersService]` only), and it batches `Cleaner`/`Team`'s own relation, not `Booking`'s. `BookingRelationLoaders` holds four `DataLoader`s — `customerLoader`, `propertyLoader`, `serviceLoader`, `teamLoader` — each built from a standalone exported batch-function (`createCustomerBatchFn`, etc.), mirroring `active-pricing.loader.ts`/`cleaner-team.loaders.ts`'s extracted-function technique so each batch function is unit-testable without reaching into `DataLoader`'s private `_batchLoadFn`. `teamLoader`'s batch function reuses `TeamsService.getTeamsByIds` (no new method needed there).
- **`CreateBookingCommand.actorId`/`UpdateBookingCommand.actorId` are typed `string | null`, not `string`, and `BookingsService.create`/`.update`/`.remove` skip the `auditLogger.log()` call entirely when `command.actorId === null`.** **Stated as its own invariant, precisely because a future implementer could otherwise misread it: `actorId: null` means no audit event is emitted for this call, full stop — it does not mean "emit an audit event with a null/anonymous actor."** `AuditEventEntity.actorId` being a nullable column (no FK to `AdminUserEntity`) is an unrelated, pre-existing fact about that column's schema — it is not license to log a null-actor event here; the `if (command.actorId !== null)` guard exists specifically so that path is never reached from REST. Spec §4.4 states REST endpoints "remain unauthenticated and unaudited in application code" for reads **and mutations alike** — not merely unauthenticated. Since `BookingsService`'s create/update/remove is the one shared implementation both transports call (spec §5's "one shared command" architecture), and GraphQL's own resolver is the only caller with a real `AuthenticatedPrincipal` to source an actor from, the REST controller (Task 3) always constructs its command with `actorId: null` — an explicit, type-checked signal meaning "this call must not produce an audit event," not a fake actor identity standing in for a real one. This was a revision from this plan's first draft, which passed a literal string (`'rest-unauthenticated'`) as `actorId` — that still caused every REST mutation to write a real `audit_event` row, which is not "unaudited," just audited-with-a-fake-actor; it directly contradicted spec §4.4 rather than implementing it. The corrected design produces zero `audit_event` rows for any REST-originated call, verified by a dedicated test (Task 2's level-2 suite).
- **Cross-module `NotFoundException` messages use this codebase's existing interpolated-id convention** (`` `Customer ${customerId} not found` ``, `` `Property ${propertyId} not found` ``, `` `Service ${serviceId} not found` ``, `` `Team ${teamId} not found` ``, `` `Booking ${id} not found` ``) rather than the spec prose's simplified phrasing — matching every existing `NotFoundException` call site in this codebase (`CustomersService`, `PropertiesService`, `ServicesService`, `BookingsService`'s own existing `findEntity`). `BadRequestException` messages use the spec's own §4.2 prose verbatim (`'Property does not belong to the given customer'`, `'Service is not active'`, `'Service has no active price'`) so specification and implementation don't drift into paraphrase, matching the Catalog plan's precedent for its own error strings.
- **`update`'s persistence uses `manager.update()`, not `Object.assign(entity, changes)` + `manager.save(entity)`** — a change from the current `BookingsService.update`'s `Object.assign`/`save()` implementation, for the audit-unconditionality reason spec §4.4 states explicitly ("every successful call — including an `updateBooking` that resubmits already-current values — ... still emits its audit event unconditionally"): `save()`'s change-diffing can produce a no-op `UPDATE` for a resubmit-same-values call, which this codebase's `updateService`/`updateCleaner`/`updateCustomer` precedent already treats as a defect to avoid via `manager.update()`'s diff-independent bulk predicate update. `Booking` has no `updatedAt` column to bump (spec §4.1), so unlike those three precedents this is purely about guaranteeing the write (and therefore the audit event) always executes, not about an `updatedAt` guarantee.
- **`teamId` presence-vs-value handling in `update` mirrors `CustomersService.update`/`PropertiesService.update`'s existing "command only carries provided keys" pattern exactly**: `UpdateBookingCommand`'s `teamId?: string | null` is built by the resolver/controller via object spread of the caller's input, so an omitted `teamId` is genuinely absent as a key (`undefined`), distinguishable from an explicitly-provided `null`. `BookingsService.update` checks `command.teamId !== undefined` to decide whether to re-validate/include it in the `manager.update()` payload at all; `command.teamId === null` clears it without a `TeamsService.getTeam` call (nothing to validate); any other value re-validates via `TeamsService.getTeam` before being included.
- **The embedded `pricingSnapshot` column's generated name is confirmed as `pricingSnapshotPriceMinorUnits`** — TypeORM's default naming strategy (property-name-prefixed), left unmodified, since no custom `NamingStrategy` exists anywhere in `data-source.ts` today. This satisfies spec §4.1's M4-verification flag; no further naming decision is needed.
- **The generated `pnpm migration:generate` output for this migration must be hand-trimmed of spurious drops/re-adds of *other* modules' hand-added FK constraints** (`fk_property_customer`, `fk_cleaner_team`, `fk_pricing_rule_service`) — TypeORM's entity-vs-schema diff always flags these as drift because none of them is modeled via a relation decorator (each of those migrations' own comments already document this). This is the same by-hand cleanup step `AddPricingRule`'s migration already performed; Task 2 repeats it for whatever spurious statements this migration's generation run emits.
- **Cross-module fixture seeding (Customer/Property/Service/Team) moves to `platform/database/seed.ts`, using the plain CLI `dataSource` — not into `BookingsModule`, and not through the application-layer `create` methods.** No other module in this codebase has a seeder today (`platform/database/seed.ts` calls only `BookingSeeder.seed()`), so spec §4.1's "referencing ids already seeded by another module's seeder" alternative does not literally apply — but the codebase already has an established precedent for exactly this situation: `seedDevOwner()`, in the same `seed.ts` file, already upserts an `AdminUserEntity` row directly via the plain CLI `dataSource` (`dataSource.getRepository(AdminUserEntity).upsert(...)`), completely bypassing Nest's module/DI boundaries — `data-source.ts`'s `entities` array already registers every entity in the system on this one shared `DataSource`, specifically so CLI-level tooling (migrations, this kind of ad hoc seed) doesn't need to go through module wiring at all. This plan's first draft instead added `CustomerEntity`/`PropertyEntity`/`ServiceEntity`/`TeamEntity` as new repository-token imports directly into `BookingsModule`, which would have given the Bookings module infrastructure-level knowledge of four other modules' entities — a real architectural smell, and a needless one given `seedDevOwner`'s precedent already solves this exact problem without it. The application-layer `create` methods (`CustomersService.create`, etc.) are deliberately **not** used for this either: they are plain-insert, non-upsert operations (`@PrimaryGeneratedColumn('uuid')`, no `upsert()` path), so calling them from a re-runnable seed script would either duplicate fixture rows on every `pnpm db:seed` run or throw `ConflictException` on `Service`/`Team`'s name-uniqueness constraints on the second run — only a raw repository `.upsert([...], ['id'])` against a fixed, deterministic id gives the idempotency `pnpm db:seed` requires, exactly as the existing `BookingSeeder`/`seedDevOwner` already do it. `BookingsModule` itself gains **no new entity imports and no new `imports` beyond `AuditModule`/`CustomersModule`/`CatalogModule`/`CleanersModule`** (all needed by `BookingsService` itself, Task 2) — `BookingSeeder` stays scoped to `BookingEntity` only, unchanged in shape from today. Full mechanism in Task 5.
- **The four create-flow selects (customer/property/service/team) are plain `<select>` elements with a manual `<label>`, not `packages/ui`'s `FormField`.** Spec §4.6 says "Forms use `FormField` from `packages/ui`; no screen hand-rolls its own inputs" — read literally against enumerated-choice controls, this plan cannot comply: `packages/ui/src/form-field.tsx` is confirmed, by reading its actual source, to wrap only an `<input>` (`export interface FormFieldProps extends InputHTMLAttributes<HTMLInputElement>`, no `as`/children/select variant exists anywhere in `packages/ui`). Critically, this is not a new deviation this plan is introducing: the identical spec sentence appears in — and governs — the already-shipped `/app/*` screens, and both `apps/web/app/app/admin/page.tsx` (the `role` dropdown) and `apps/web/app/app/cleaners/page.tsx` (the team-assignment select) already use a raw `<select>` with a hand-written `<label htmlFor>` for their own enumerated-choice fields, under this exact same governing convention. That precedent is the actual, established reading of "no screen hand-rolls its own inputs" in this codebase: the sentence targets ad hoc `<input>` elements that bypass `FormField`'s label/error/aria wiring, not enumerated-choice controls `FormField` cannot represent at all. This plan's selects follow that precedent's exact shape (manual `<label htmlFor>`, matching Tailwind classes) rather than inventing a new pattern; `FormField` is still used for `scheduledAt` (Task 6), the one field in this flow that is a genuine text/date input. If a `packages/ui` `Select` primitive is ever added, these four call sites are the natural place to adopt it — not a blocker for this slice.
- **The three new bulk methods (Task 1) return `[]` immediately for an empty `ids` array, without querying** — `if (ids.length === 0) { return []; }` before the `findBy({ id: In(ids) })` call in each of `getCustomersByIds`/`getPropertiesByIds`/`getServicesByIds`. `TypeORM`'s `In([])` behavior for an empty array is not relied upon either way; this makes the empty-input contract explicit rather than incidental, and avoids depending on a specific TypeORM/Postgres version's handling of `WHERE id IN ()`.
- **No new environment variables or secrets, no new npm dependency** — `dataloader` is already installed and approved (Cleaners & Teams M5).

  private async resolveAndValidate(
    command: CreateBookingCommand,
  ): Promise<{ pricingSnapshot: BookingPricingSnapshot }> {

    if (!customer) throw new NotFoundException(`Customer ${command.customerId} not found`);

    if (!property) throw new NotFoundException(`Property ${command.propertyId} not found`);
    if (property.customerId !== command.customerId) {
      throw new BadRequestException('Property does not belong to the given customer');
    }

    if (!service) throw new NotFoundException(`Service ${command.serviceId} not found`);

    if (!pricing) throw new BadRequestException('Service has no active price');

      const team = await this.teamsService.getTeam(command.teamId);
      if (!team) throw new NotFoundException(`Team ${command.teamId} not found`);

    return { pricingSnapshot: { priceMinorUnits: pricing.priceMinorUnits } };
