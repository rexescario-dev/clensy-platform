Where this plan and the Accepted specification disagree, the specification wins and this plan must be revised.

**Goal:** Build a new `modules/billing` that generates an immutable `Invoice` + `InvoiceLine` snapshot from a priced `LaundryOrder`, exposes it over GraphQL and a `/app/billing` web view, and establishes the payment-state model without recording payments or computing discounts.

**Architecture:** `modules/billing` mirrors the established domain → application → infrastructure → presentation layering of `modules/laundry`. `InvoicesService.generateFromOrder` reads the order + its lines through one new additive `LaundryOrdersService` method, copies each line's resolved figures and the catalog name into an `InvoiceLine`, computes integer totals with a pure function, draws a human-readable number from a dedicated Postgres sequence, and writes everything in one audited transaction guarded by a `UNIQUE(laundryOrderId)` constraint. The only mutation is `generateInvoiceFromOrder`, gated to `FINANCE`/`OWNER`.

**Tech Stack:** NestJS, `@ptc-org/nestjs-query-graphql` / `-typeorm`, TypeORM + PostgreSQL, Jest (unit + e2e), Next.js App Router + `packages/ui`, GraphQL codegen (`packages/client`).

**Spec:** [`docs/superpowers/specs/2026-09-06-laundry-invoices-design.md`](../specs/2026-09-06-laundry-invoices-design.md) (Accepted). The plan argues from the spec; executors read both.

## Global Constraints

Copied verbatim from the Accepted spec — every task's requirements implicitly include this section:

- All money is **integer minor units**; **no floating-point column anywhere** in either new table (spec §4.2, §4.8).
- `amountDueMinorUnits` is **derived, never persisted** — `totalMinorUnits - amountPaidMinorUnits`, computed in the GraphQL type and every read consumer (spec §3, §4.2, §4.7).
- In this ticket: `discountMinorUnits` is always `0`, `amountPaidMinorUnits` is always `0`, `paymentStatus` is always `UNPAID` at generation; the generation operation accepts **no** discount input (spec §1, §4.5, §8).
- After generation the invoice's commercial snapshot — `invoiceNumber`, `laundryOrderId`, `customerId`, `subtotalMinorUnits`, `discountMinorUnits`, `totalMinorUnits`, `paymentTerms`, `issueDate`, `dueDate` — and every `InvoiceLine` field are immutable; `amountPaidMinorUnits` and `paymentStatus` are the designated #39 mutation surface and #38 has no operation that changes them after writing `0` / `UNPAID` (spec §1, §4.4, §4.8).
- Exactly one `Invoice` per `LaundryOrder`; the `UNIQUE(laundryOrderId)` constraint — **not** the application pre-check — is the correctness mechanism (spec §4.3, §4.6, §4.8).
- `invoiceNumber` = `INV-{issueYear}-{6-digit zero-padded sequence}`; `issueYear` is the **`Asia/Manila`** calendar year of `issueDate`; `issueDate` is a UTC `timestamptz`; the sequence is global, never resets, and is **gap-tolerant** — a rolled-back generation burns its value and this must not be "fixed" into a gapless counter table (spec §3, §4.5, §4.6).
- Eligibility: `order.totalMinorUnits !== null`, `order.status` in `PRICED … COMPLETED` (`PRICED`, `AWAITING_PAYMENT`, `PAID`, `PROCESSING`, `READY`, `AWAITING_PICKUP`, `AWAITING_DELIVERY`, `COMPLETED`) and **not** in `{CANCELLED, REJECTED, LOST, DAMAGED, REFUNDED}`, `order.lines` non-empty, no existing `Invoice` (spec §4.3).
- `InvoiceLine` holds **no** FK or id pointer to `service_entity` / `add_on_entity` / `pricing_rule_entity` / `laundry_order_line_entity`; `description` is the catalog name frozen at generation; every other line field is a verbatim copy of the source `LaundryOrderLine.pricingSnapshot` — **no recomputation** (spec §3, §4.2, §4.4).
- `generateInvoiceFromOrder` is the **only** mutation; `@UseGuards(AuthGuard)` + `@Roles(Role.FINANCE, Role.OWNER)`. Reads use `AuthGuard` + the six-role `VIEW_ROLES` set at **every** entry point — root connection, `invoice(id)`, nested `lines`, relation fields (spec §4.7, §4.8).
- `InvoicePaymentStatus` = `UNPAID | PARTIALLY_PAID | PAID | VOID` (full set defined now; `VOID` is an invoice-lifecycle state, not a payment outcome; #38 never produces it). `InvoicePaymentTerms` = `PAY_NOW | PAY_ON_COMPLETION | PAY_ON_DELIVERY` (required input). `dueDate` = `issueDate` for `PAY_NOW`, else `null` (spec §3, §4.2, §4.5).
- `0 <= amountPaidMinorUnits <= totalMinorUnits` is an application/domain invariant, **not** a DB `CHECK` in #38; satisfied at generation by writing `0`; #39 owns preserving it (spec §4.5).
- The migration creates **only** billing-owned objects — nothing in `modules/laundry`, `modules/catalog`, or `modules/customers` (spec §4.9).
- The only changes to other modules are **two additive read methods**: `LaundryOrdersService.getOrderForInvoicing` and `AddOnsService.getAddOnsByIds`. No existing method, entity, contract, or lifecycle in `modules/laundry` / `modules/catalog` changes (spec §2, §4.1).
- No tax field/column/logic; no invoice correction/void/reissue/edit/delete; no `Payment`; no discount computation; no print/PDF pipeline; no customer-facing access; no REST surface; no persisted `amountDueMinorUnits`; no composite sort index (spec §2, §8).

## 1. Delivery intent

Implement exactly what the Accepted spec authorizes: a new `modules/billing` with the `Invoice` / `InvoiceLine` domain (spec §4.2), the `InvoicePaymentStatus` / `InvoicePaymentTerms` enums (spec §3), the pure `computeInvoiceTotals` and `formatInvoiceNumber` functions plus an `Asia/Manila` year helper (spec §4.5), `InvoicesService.generateFromOrder` as the single command routing generation through a `dataSource.transaction` + `runAuditInTransaction` guarded by `UNIQUE(laundryOrderId)` (spec §4.3, §4.4, §4.6), the TypeORM entities + a dedicated sequence + one additive migration (spec §4.9), the GraphQL read/mutation surface following the platform pagination/connection contract with `generateInvoiceFromOrder` as the only mutation (spec §4.7), the two additive cross-module reads (spec §4.1), and the `/app/billing` web page + laundry-drawer "Invoice" section built from existing `packages/ui` primitives (spec §4.10). No `Payment`; no discount input; no tax; no invoice mutation other than generate; no change to any Accepted #37/#36 contract beyond the two additive reads.

## 2. Constraints (SHALL / SHALL NOT)

**SHALL** (traced to spec section):

- `Invoice` carries exactly the §4.2 fields: `id` (uuid), `invoiceNumber` (unique string), `laundryOrderId` (uuid, FK `ON DELETE RESTRICT`, **`UNIQUE`**, immutable), `customerId` (uuid, FK → `customer_entity` `ON DELETE RESTRICT`, immutable), `subtotalMinorUnits` / `discountMinorUnits` / `totalMinorUnits` / `amountPaidMinorUnits` (integer), `paymentStatus` (PG enum), `paymentTerms` (PG enum), `issueDate` (`timestamptz`), `dueDate` (`timestamptz | null`), `createdAt` / `updatedAt`. **No** `amountDueMinorUnits` column. **No** FK/id column for `Payment` / `Promotion` / `AppliedPromotion` / loyalty / logistics (spec §4.2).
- `InvoiceLine` carries exactly the §4.2 fields: `id` (uuid), `invoiceId` (uuid, FK → `invoice_entity` `ON DELETE CASCADE`), `description` (string), `quantity` (integer), `unit` (module-local PG enum `invoice_line_unit_enum`), `rateMinorUnits` (integer), `amountMinorUnits` (integer), `createdAt` (`timestamptz`). **No** `serviceId` / `addOnId` / `pricingRuleId` / `laundryOrderLineId`; **no** `@ManyToOne` to any catalog entity; **no** `minimumChargeMinorUnits` / `minimumChargeApplied` copy (spec §4.2, §4.4).
- `InvoicePaymentStatus` = `{ UNPAID, PARTIALLY_PAID, PAID, VOID }`; `InvoicePaymentTerms` = `{ PAY_NOW, PAY_ON_COMPLETION, PAY_ON_DELIVERY }` (spec §3).
- `computeInvoiceTotals({ lineAmountsMinorUnits: number[], discountMinorUnits: number }) → { subtotalMinorUnits, totalMinorUnits }`: `subtotal = Σ lineAmounts`; precondition `0 <= discountMinorUnits <= subtotalMinorUnits` (throws on violation); `total = subtotal - discount`; integer-only, no division, no float, deterministic (spec §4.5).
- `formatInvoiceNumber(sequenceValue: number, issueYear: number) → string` = `` `INV-${issueYear}-${String(sequenceValue).padStart(6, '0')}` ``; padding to 6 digits; `> 999999` renders more digits without wrapping (spec §4.5).
- The `Asia/Manila` year of a UTC instant is resolved once, in the service, and passed to `formatInvoiceNumber` as `issueYear` (spec §3, §4.5).
- `InvoicesService.generateFromOrder({ actorId, laundryOrderId, paymentTerms })`:
  - captures one `issueDate = new Date()` at the start (spec §4.4 step 1);
  - `order = LaundryOrdersService.getOrderForInvoicing(laundryOrderId)` → `NotFoundException` if `null` (spec §4.4 step 2);
  - eligibility checks (spec §4.3) throw `BadRequestException` (not priced / excluded status / no lines) or `ConflictException` (already invoiced) **before** the write transaction opens (spec §4.3, §4.4 step 3);
  - resolves line descriptions via `ServicesService.getServicesByIds` + `AddOnsService.getAddOnsByIds`; **every referenced id MUST resolve** — a missing one → `BadRequestException` before the transaction (spec §4.4 step 4);
  - builds each `InvoiceLine` by copying `quantity` / `unit` / `rateMinorUnits` / `amountMinorUnits` from the source `LaundryOrderLine.pricingSnapshot` verbatim and `description` = the resolved `Service.name`, or `` `${AddOn.name} (add-on)` `` for an add-on line (spec §4.4 step 5);
  - `computeInvoiceTotals({ lineAmountsMinorUnits, discountMinorUnits: 0 })` (spec §4.4 step 6);
  - `dueDate = paymentTerms === PAY_NOW ? issueDate : null` (spec §4.4 step 7, §4.5);
  - inside `dataSource.transaction((manager) => runAuditInTransaction(manager, …))`: re-check no existing invoice for the order (application pre-check for a clean `ConflictException`); `SELECT nextval('billing_invoice_number_seq')`; `formatInvoiceNumber(seq, manilaYearOf(issueDate))`; `manager.save` the `InvoiceEntity` (`customerId` = `order.customerId`, `discountMinorUnits: 0`, `amountPaidMinorUnits: 0`, `paymentStatus: UNPAID`, `paymentTerms`, `issueDate`, `dueDate`, `subtotalMinorUnits`, `totalMinorUnits`); `manager.save` every `InvoiceLineEntity`; `auditLogger.log({ actorId, action: 'invoice.generated', entityType: 'invoice', entityId })`; return the re-read invoice (spec §4.4 step 8, §4.6);
  - on `uq_invoice_laundry_order` violation → translate to `ConflictException` (constraint-scoped helper); on `uq_invoice_number` violation → **rethrow as-is** (integrity error, never a business conflict) (spec §4.6, §4.8);
  - the whole transaction (invoice + lines + audit) commits or rolls back atomically; a losing concurrent generation leaves **no** invoice, **no** lines, **no** `invoice.generated` audit row (a burned sequence value is acceptable) (spec §4.6).
- `LaundryOrdersService.getOrderForInvoicing(id): Promise<OrderForInvoicing | null>` — **new, additive** — returns `{ id, customerId, status, totalMinorUnits, lines: { serviceId, addOnId, pricingSnapshot: { quantity, unit, rateMinorUnits, amountMinorUnits } }[] }` (or `null`). Read-only projection; changes no existing `LaundryOrdersService` method, no `LaundryOrder` contract, no entity registration (spec §4.1).
- `AddOnsService.getAddOnsByIds(ids: string[]): Promise<AddOn[]>` — **new, additive** — `ids.length === 0 ? [] : addOnRepository.findBy({ id: In(ids) })`, exactly mirroring `ServicesService.getServicesByIds`; returns only rows that exist (spec §4.1).
- GraphQL reads follow the platform contract: `invoices` root offset Connection (`{ nodes, pageInfo, totalCount }`, `paging` default `{ limit: 20 }`, max 100, default sort `issueDate DESC, createdAt DESC, id ASC`); `invoice(id: ID!): Invoice` single **nullable** hand-written query (`one: { disabled: true }`); `Invoice.lines` nested offset Connection (`{ nodes, pageInfo }`, **no** `totalCount`, default sort `createdAt ASC, id ASC`) (spec §4.7).
- Every read entry point — the `ReadResolver`, the nested `lines` connection, the `invoice(id)` query, the `customer` / `laundryOrder` relation fields — is guarded by `AuthGuard` + `@Roles(...VIEW_ROLES)` (spec §4.7).
- `InvoiceType` exposes all `Invoice` fields plus a computed `amountDueMinorUnits: Int!` resolve-field = `totalMinorUnits - amountPaidMinorUnits`; `registerEnumType` for both enums; batched `customer: CustomerType!` and `laundryOrder: LaundryOrderType!` resolve-fields via request-scoped DataLoaders (spec §4.7).
- `GenerateInvoiceFromOrderInput { laundryOrderId: ID!, paymentTerms: InvoicePaymentTerms! }` (spec §4.7).
- `paginated-collections-allowlist.e2e-spec.ts` gains a `ROOT_CONNECTIONS` row (`invoices` / `InvoiceConnection` / `InvoiceSortFields` / `['issueDate','createdAt','id']`) and a `NESTED_CONNECTIONS` row (`Invoice.lines` / `InvoiceLineSortFields` / `['createdAt','id']`); the generated-CRUD / generic-mutation assertions still pass (no `createOneInvoice`, `updateOneInvoice`, `deleteOneInvoice`) (spec §4.7).
- One additive migration `<epoch>-CreateBillingInvoices.ts`: `CREATE SEQUENCE billing_invoice_number_seq`; three `CREATE TYPE`; `invoice_entity` (with `uq_invoice_number`, `uq_invoice_laundry_order`, index on `customerId`, index on `paymentStatus`, FK `fk_invoice_laundry_order` `RESTRICT`, FK `fk_invoice_customer` `RESTRICT`); `invoice_line_entity` (FK `fk_invoice_line_invoice` `CASCADE`, index on `invoiceId`). `down()` dependency-safe: drop line FKs + invoice FKs → `DROP TABLE invoice_line_entity` → `DROP TABLE invoice_entity` → `DROP TYPE invoice_line_unit_enum` → `DROP TYPE invoice_payment_terms_enum` → `DROP TYPE invoice_payment_status_enum` → `DROP SEQUENCE billing_invoice_number_seq`. Touches **no** non-billing object (spec §4.9).
- `/app/billing` is one route built only from existing `packages/ui` primitives + the `/app/*` shell: a `DataTable` list (number, customer, total, amount due, `paymentStatus` `StatusBadge`, issue date), a `?detail=` `DetailDrawer` (header + amounts + terms + dates + `lines`). No generation form on this route (spec §4.10).
- The `/app/laundry` order detail drawer gains an additive "Invoice" section: a "Generate invoice" control (with a `paymentTerms` `<select>`) when the order is eligible and has no invoice, shown only to a `FINANCE`/`OWNER` actor (presentation mirror; server authoritative); once an invoice exists, its number / total / `paymentStatus` + a link to `/app/billing?detail=<id>` (spec §4.10).

**SHALL NOT** (explicit spec non-goals — do not invent):

- No `Payment` entity/service/surface; no mutation of `amountPaidMinorUnits` or `paymentStatus` after generation; no operation producing `InvoicePaymentStatus.VOID` (spec §2, §8).
- No `Promotion` / `AppliedPromotion`; no caller-supplied discount; `discountMinorUnits` is hardcoded `0` at generation (spec §2, §8).
- No `taxMinorUnits` column, field, or logic (spec §2, §8).
- No invoice correction / regeneration / void / reissue / edit / delete mutation; no credit-note document (spec §2, §8).
- No `serviceId` / `addOnId` / `pricingRuleId` / `laundryOrderLineId` column on `invoice_line_entity`; no `@ManyToOne` from `InvoiceLineEntity` to any catalog entity (spec §4.2, §5).
- No persisted `amountDueMinorUnits`; no composite `(issueDate, id)` / `(invoiceId, createdAt, id)` sort index (spec §4.9, §8).
- No change to any existing `LaundryOrdersService` / `AddOnsService` method, any `modules/laundry` or `modules/catalog` entity/contract/lifecycle, or `resolveEffectivePricing` — only the two new additive reads (spec §2, §4.1).

- No REST controller for billing; no customer-facing invoice access; no print / PDF rendering pipeline (spec §2, §8).
- No new npm dependency (`Asia/Manila` conversion uses the platform's existing capability — see §3); no gapless counter table for invoice numbering (spec §4.5).

- **`registerEnumType(InvoicePaymentStatus, { name: 'InvoicePaymentStatus' })`** and `registerEnumType(InvoicePaymentTerms, { name: 'InvoicePaymentTerms' })` are called once each in `invoice.type.ts` (first GraphQL use), mirroring `laundry-order.type.ts`.

## 9. Execution / dependency risks

- **`ReadResolver` `one` nullability.** nestjs-query's generated single-entity query is non-null / throws on miss; the spec wants a nullable `invoice(id)`. Mitigation: `one: { disabled: true }` + a hand-written `@Query(nullable: true)` — the `LaundryOrderResolver` precedent; Tasks 20–21 follow it exactly.
- **Nested-connection registration.** `InvoiceLineEntity` must be registered with `NestjsQueryTypeOrmModule.forFeature` (and `InvoiceLineType` in the `dtos` array) for `Invoice.lines` to resolve; the allowlist test catches a missing `InvoiceLineConnection` / `InvoiceLineSortFields`. Tasks 17 + 22, derived from the real `laundry.module.ts` code first.
- **`migration:generate` drift.** TypeORM's `@Index(..., { unique: true })` may generate a unique *index* rather than a named `UNIQUE constraint`; the `constraint` field on a `23505` error differs between the two (`uq_...` vs the index name). Task 11 must confirm what name Postgres reports for a `laundryOrderId` collision and Task 13/15 must match `isPostgresUniqueViolation`'s expected constraint string to it (the `jobs` `UQ_cleaning_job_booking_id` precedent — a unique index whose name is what the driver reports). Verify with a real duplicate insert in the Task 11 introspection step.
- **`Intl` / `Asia/Manila` availability.** If the Node runtime lacks full ICU (unlikely on the targeted version, but check), `Intl.DateTimeFormat` with `timeZone: 'Asia/Manila'` throws or silently returns UTC. Task 15 includes a one-line runtime check; the documented fallback is a fixed `+08:00` offset (Manila has no DST) applied before `getUTCFullYear()`. `resolveIssueYear` has its own boundary-case unit test either way.
- **`customer` / `laundryOrder` resolve-field batching.** If `CustomersService` / `LaundryOrdersService` expose no `getXsByIds`, the loader either batches single reads or a new additive batch method is added. Task 19 resolves this by reading the existing `bookings` / `jobs` customer resolve-field first — do not invent a pattern.
- **`schema.gql` timing for `packages/client`.** Slice G Task 27 must run after Slice E has emitted the updated `apps/api/src/schema.gql`. Sequence enforced by the slice order.
- **Client codegen scope.** `pnpm --filter @clensy/client codegen` regenerates from all `src/**/*.graphql`; the only new document is `billing.graphql`, so the diff must be additive — verify no unrelated operation changed.
- **Generation atomicity.** `generateFromOrder` creates the invoice + N lines + the audit event; a failure at any point (catalog id unresolved after the transaction opens — shouldn't happen, checked before; a DB error; the unique race) must leave zero rows and no audit event. The single `dataSource.transaction` wrapping the whole write body provides this; the Task 26 concurrent-race e2e is the check.
- **Excluded-status list must track #37.** The eligibility range is `PRICED … COMPLETED` minus `{CANCELLED, REJECTED, LOST, DAMAGED, REFUNDED}`. If #37's `LaundryOrderStatus` ever gains an ordinary-fulfilment state, this spec (§4.3) re-enters review — the plan encodes the range against the enum, not a copy of the string list, and Task 15 comments this.
- **Two additive reads on Accepted modules.** Slices B changes `laundry-orders.service.ts` and `add-ons.service.ts`. The risk is a reviewer reading it as a #37/#36 redesign. Mitigation: Slice B is deliberately isolated and its two tasks each run the owning module's full existing spec to prove no behavior change; the spec (§4.1) authorizes exactly these two additive reads by name.
