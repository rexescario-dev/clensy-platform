## 1. Primary question & thesis

**Question:** `modules/bookings` is the one existing business module in this codebase — pre-dating Admin Foundation, RBAC, audit, and every architectural convention the other five Phase-1 slices were built against from day one. What does it mean to bring it into parity with those conventions while satisfying the issue's explicit "migration, not a rewrite" constraint, and what exactly changes versus what stays frozen?

**Thesis:** `Booking` sheds its fake `customerName`/`serviceType` strings for real `customerId`/`propertyId`/`serviceId` references (plus an optional `teamId`), validated against `modules/customers`, `modules/catalog`, and `modules/cleaners`' application-layer read contracts — never their entities (Phase 1 Design §2.6). Every booking captures a `pricingSnapshot` (the service's active price at booking time) so a later catalog price change never retroactively changes what a historical booking appears to have cost. The GraphQL surface gains RBAC and audit logging, bringing it to parity with every other module built after Admin Foundation. The REST surface — kept only as this project's original REST-vs-GraphQL comparison artifact (Phase 1 Design §7's "no redesign of the existing Booking REST contract") — keeps its routes, verbs, response envelope (HTTP status codes, error format), and its pre-existing absence of auth/RBAC/audit exactly as they are today; its DTOs' field names, and consequently its response bodies' fields, move in lockstep with the one shared `CreateBookingCommand`/`UpdateBookingCommand` contract both transports have always mapped into (see §5 for why literal field preservation is not achievable, or intended, here). `BookingStatus` and its transition-free update semantics are unchanged. This is Phase 1's first slice where a module's application layer actively reads across three other modules' contracts in the same request — the "cross-module integration is actually exercised" milestone the issue names it as.

## 2. Scope

### In scope (normative)

- `modules/bookings` domain: `Booking` updated to hold `customerId`, `propertyId`, `serviceId`, `teamId` (nullable), `scheduledAt`, `status`, and a new `pricingSnapshot` value object (plain TS, no framework dependencies) in place of `customerName`/`serviceType`.
- Application layer: `CreateBookingCommand`/`UpdateBookingCommand` updated to the new shape; `BookingsService.create` resolves and validates `customerId`/`propertyId`/`serviceId`/`teamId` via `modules/customers`, `modules/catalog`, and `modules/cleaners`' existing application read contracts (§4.2) — never those modules' entities or repositories, per Phase 1 Design §2.6.
- Infrastructure: `BookingEntity` migrated from flat fake columns to FK columns (`customerId`, `propertyId`, `serviceId`, `teamId`) plus the pricing-snapshot column(s); a real migration (not `synchronize`), per this codebase's existing convention. No backfill strategy is in scope — see the Legacy data migration note at the end of §4.1 for why.
- Presentation:
  - GraphQL: `BookingType`/`CreateBookingInput`/`UpdateBookingInput` updated to the new relation fields; `BookingType` gains computed `customer`/`property`/`service`/`team` fields (§4.5); every operation gains `AuthGuard` + `@Roles()` (§4.3) and every mutation gains audit logging (§4.4) — bringing `bookings` to parity with every other Phase-1 module.
  - REST: `CreateBookingDto`/`UpdateBookingDto` field names updated to match the new shared command, and response bodies updated in lockstep since there is no separate REST view-model layer (they cannot do otherwise — see §5); routes, HTTP verbs, response envelope (status codes, error format), Swagger docs pattern, and the REST controller's pre-existing absence of `AuthGuard`/RBAC/audit are all left exactly as they are today. This is the one place this slice deliberately does **not** bring `bookings` to parity with the rest of the codebase — see §5's rationale.
- `apps/web`: `/app/bookings` — list (`DataTable`) + create (`FormDialog` with cascading customer → property → service → team selects) + inspect/edit (`DetailDrawer`) + delete (`ConfirmDialog`, explicitly worded as a permanent, irreversible action — not "cancel," §4.6), on the `/app/*` shell and primitives from Dashboard UX Foundation (§4.6).
- Tests: unit tests for `BookingsService` (application layer) covering the new validation chain (§4.2), updated for both GraphQL and REST presentation-layer tests to the new DTO/Input shapes, and one e2e covering the full create-booking golden path across all four dependent modules (customer → property → service + active pricing → booking, per the issue's own DoD) — named this way because `PricingRulesService.getActivePricing` is itself a required step in the validation chain (§4.2 step 4), not an incidental detail the golden path can skip past. **A second, dedicated integration/e2e test is required (added per M3 round 2) for the specific invariant this migration exists to guarantee (§1, §4.1): create a booking against an active `PricingRule`, then change that service's active pricing (deactivate the old rule, activate a new one at a different `priceMinorUnits`), then re-fetch the original booking and assert its `pricingSnapshot.priceMinorUnits` is unchanged.** A companion assertion covers the `scheduledAt`-is-irrelevant-to-pricing claim in §4.1: create a booking with `scheduledAt` set weeks in the future against today's active pricing, and assert the snapshot reflects today's price, not a hypothetical future one — there is no effective-dated lookup to accidentally exercise, but the test exists so a future regression that adds one would be caught. Immutable-after-creation is also normatively asserted, not just documented: attempting to submit `customerId`, `propertyId`, or `serviceId` via `updateBooking`/`PATCH /bookings/:id` MUST be rejected at the DTO/Input level (the fields do not exist on `UpdateBookingCommand`, §4.2) — covered by a presentation-layer test per transport — while `teamId` MUST be exercisable through its full range: assigned on an initially-unassigned booking, reassigned to a different team, and cleared back to `null`.

### Out of scope (normative)

- Any change to `BookingStatus`'s four values or to `updateBooking`'s status-transition validation — there is none today (any status value is accepted unconditionally) and this slice adds none. "Status model preserved" (issue DoD) means exactly this: unchanged.
- Availability/conflict checking (e.g. rejecting a second booking for an already-booked time slot or an already-assigned team) — a genuinely new business rule the issue's DoD does not ask for. Deferred, not assumed away; a future slice that wants it must specify the conflict semantics explicitly.
- Re-snapshotting or recalculating `pricingSnapshot` after creation — there is no operation in this slice that changes `serviceId` or refreshes the captured price on an existing `Booking` (§4.1, §4.2).
- Any relationship to `modules/jobs` or `modules/quality` — those are M7/M8's concern per Phase 1 Design §4's dependency order; a booking's relationship to the job(s) it generates is deliberately not modeled here (Phase 1 Design §2.3: "a booking can outlive/precede/diverge from the job(s) it generates").
- A dedicated `assignBookingTeam` mutation mirroring the Cleaners spec's `assignCleanerToTeam` — considered and declined; `teamId` is a plain field of `CreateBookingInput`/`UpdateBookingInput` instead. See §5 for why this slice does not follow that precedent.
- Any new UI primitive (e.g. a multi-step wizard component) — the create flow's "customer → property → service → team" walk is modeled as one `FormDialog` with dependent/cascading selects, not a multi-page wizard, since `packages/ui` ships no stepper primitive and this slice does not add one (§4.6, §5).
- Cascading delete behavior for `customerId`/`propertyId`/`serviceId`/`teamId` — moot in practice, since none of `Customer`, `Property`, `Service`, or `Team` has a delete operation anywhere in Phase 1 today, but the FK `ON DELETE` policy is still stated explicitly (§4.1), per this codebase's established precedent of deciding it rather than inheriting a default.
- Currency, multi-currency, or money-representation changes — `pricingSnapshot.priceMinorUnits` reuses Catalog's existing integer-minor-units, implicit-PHP convention unchanged (Catalog spec §5, §7).
- REST gaining `AuthGuard`, `@Roles()`, or audit logging — explicitly declined; see §5.

## 3. Terminology

- **Booking** — a `modules/bookings` domain object representing what a customer actually booked: a specific `Property`, a specific `Service`, at a specific time, with a price snapshot and (optionally) a `Team` assigned to perform it.
- **Pricing snapshot** — a `Booking`-owned value object capturing the `Service`'s active price at the moment of booking creation, so a later `catalog` price change does not retroactively change what a historical booking appears to have cost (Phase 1 Design §2.3). Not itself a persisted, independently addressable entity — it lives only as part of its owning `Booking`.
- **Reference-only relation** — the Phase 1 Design §2.6 rule that `Booking` holds `customerId`/`propertyId`/`serviceId`/`teamId` as plain identifiers, never `CustomerEntity`/`PropertyEntity`/`ServiceEntity`/`TeamEntity` or any direct import from those modules' infrastructure or domain layers.
- **Actor** — the `AuthenticatedPrincipal` performing a mutation, threaded into `AuditLogger` calls as `actorId`, per the Admin Foundation contract (unchanged here).
- **Cancel** vs. **Delete** — two distinct, unrelated operations in this slice, not synonyms (resolved M3 round 1). *Cancelling* a booking means calling `updateBooking` with `status: CANCELLED`; the row, its `pricingSnapshot`, and its relations remain intact and queryable — a normal, non-destructive status transition, exactly as available today. *Deleting* a booking means calling `removeBooking`/`DELETE /bookings/:id`, which hard-deletes the row; nothing about it is recoverable afterward. Neither this module's API nor its web UI may use "cancel" language to describe the delete operation, or vice versa — see §4.6 and §5 for why the pre-revision draft conflated them and how that is fixed.

## 4. Domain and behavioral contracts

### 4.1 Domain objects

`Booking`:
- `id: string` (UUID, generated; not client-settable)
- `customerId: string` (required; references `modules/customers`' `Customer.id`; immutable after creation — see §4.2 for why)
- `propertyId: string` (required; references `modules/customers`' `Property.id`; MUST belong to `customerId`, §4.7; immutable after creation)
- `serviceId: string` (required; references `modules/catalog`'s `Service.id`; MUST be `active` at booking time, §4.7 — the exact consumer responsibility Catalog's spec §4.1 hands to "a downstream module that needs services available for a new booking"; immutable after creation)
- `teamId: string | null` (optional; references `modules/cleaners`' `Team.id`; `null` means unassigned at booking time. Unlike `customerId`/`propertyId`/`serviceId`, this field is mutable after creation via `updateBooking` — a deliberate divergence from the other three FKs and from the Cleaners spec's `assignCleanerToTeam`-as-a-separate-operation precedent; see §5)
- `scheduledAt: Date` (required; unchanged from today)
- `status: BookingStatus` (unchanged enum: `PENDING | CONFIRMED | CANCELLED | COMPLETED`; unchanged transition-free update semantics, §2)
- `pricingSnapshot: BookingPricingSnapshot` (required; set once at creation, never mutated afterward — see below)
- `createdAt: Date` (set once at creation; not client-settable)

`BookingPricingSnapshot` (new value object):
- `priceMinorUnits: number` (the `PricingRule.priceMinorUnits` active for `serviceId` at the moment `createBooking`/`POST /bookings` executed — see §4.2)

**Pricing is resolved from the active pricing rule at booking-creation time, not at `scheduledAt`** (made explicit M3 round 1). A booking made today for a service date weeks out captures today's price, not a price that will be active on the future scheduled date — there is no effective-dated pricing lookup in this slice, and none should be inferred from the presence of `scheduledAt` on the same entity. If date-effective pricing becomes a real need later, that is a new, separately-specified capability for both this module and Catalog's `PricingRule` model (Catalog spec §2's own deferred "date-effective... pricing" non-goal).

Scoped narrowly to price only, not to a full point-in-time copy of the service (e.g. its name or duration) — the issue's own framing (Phase 1 Design §2.3) is specifically about cost, not about insulating a historical booking from a later `Service.name` rename. If a future need for a fuller historical snapshot emerges, that is a new, separately-specified capability, not assumed here.

`Booking` does **not** contain `customer`/`property`/`service`/`team` fields — the domain object owns only its own scalar fields and the raw FK ids, per §2.6's reference-only rule. The full related objects, when needed, are reached only through the GraphQL presentation layer (§4.5), mirroring every prior slice's precedent for computed relationship fields.

None of `customerId`, `propertyId`, `serviceId`, or `teamId` carries a TypeORM relation decorator — each is a plain `@Column({ type: 'uuid'[, nullable: true] })`, with the FK constraint hand-added to the migration's raw SQL, matching the precedent every prior slice (`Property.customerId`, `Cleaner.teamId`, `PricingRule.serviceId`) already established for this exact reason (preventing an accidental bidirectional ORM aggregate that would violate §2.6). `BookingPricingSnapshot` is persisted as a TypeORM embedded column (`@Column(() => BookingPricingSnapshot)`) rather than a second table — this is the first use of a TypeORM embedded column in this codebase (every other module's fields are flat scalars). It is used here, not a plain `priceMinorUnitsAtBooking: number` column, for one direct reason (simplified M3 round 1): the domain contract above explicitly defines the pricing snapshot as a value object, and a TypeORM embedded column is this framework's existing mechanism for persisting a value object without promoting it to an independent entity/table. M4 MUST verify the actual generated column name(s) (TypeORM's default embedded-column naming strategy prefixes with the property name, e.g. `pricingSnapshotPriceMinorUnits`) against this codebase's existing column-naming conventions before finalizing the migration — a naming detail for M4 to confirm, not a design blocker.

None of `Customer`, `Property`, `Service`, or `Team` has a delete operation anywhere in Phase 1 today (Customers & Properties, Catalog, and Cleaners & Teams specs' respective Out-of-scope sections), so the question of what happens to a `Booking` referencing a deleted row is moot in practice. The FK `ON DELETE` policy is still stated explicitly, per this codebase's established precedent of deciding it rather than inheriting a default: all four FKs are `RESTRICT`.

**Legacy data migration (added M3 round 1 — was entirely missing from the initial draft).** The existing `bookings` table contains no persisted business data, in any environment, that must be preserved: Phase 1 has no production deployment yet, and every row that exists anywhere today is exclusively the deterministic seed data written by `booking.seed-data.ts`/`booking.seeder.ts` (fixed ids `00000000-…-0001`/`…0002`/`…0003`, safely dropped and regenerated by `pnpm db:seed`). The migration MAY therefore drop the legacy `customerName`/`serviceType` columns and add the new FK/pricing-snapshot columns directly — no backfill, no deterministic-mapping step, and no "unmappable row" handling are required, because there is nothing to map. This is a factual claim about this project's current deployment state, not a general policy; if a later milestone ever runs this migration against an environment that does carry real booking data, that environment's operator must design a backfill separately — this specification does not claim its no-backfill approach generalizes past Phase 1's current, pre-production state. As a direct consequence, `booking.seed-data.ts`/`booking.seeder.ts` MUST be updated in this same slice to seed valid `customerId`/`propertyId`/`serviceId` values (e.g. by seeding a matching customer/property/service first, or referencing ids already seeded by another module's seeder) — continuing to seed the old fake-string shape would fail against the new schema, not merely be stale.

### 4.2 Application layer

Mirrors the existing `bookings/application/commands` + `application/services` split (unchanged file layout). `BookingsService.create` and `.update` each own their transaction boundary: the entity write and the corresponding `AuditLogger.log()` call execute within one database transaction via `runAuditInTransaction`, the exact existing pattern already used by `customers`/`cleaners`/`catalog` (Admin Foundation's transactional-audit rule, reused unchanged) — bookings did not previously use this pattern (it had no audit calls at all) and adopts it here for the first time.

- `CreateBookingCommand` → `BookingsService.create` — within one transaction, in order:
  1. `CustomersService.getCustomer(customerId)` — `NotFoundException('Customer not found')` if `null`.
  2. `PropertiesService.getProperty(propertyId)` — `NotFoundException('Property not found')` if `null`; `BadRequestException('Property does not belong to the given customer')` if the returned `Property.customerId !== customerId` (§4.7).
  3. `ServicesService.getService(serviceId)` — `NotFoundException('Service not found')` if `null`; `BadRequestException('Service is not active')` if `!service.active` (§4.7 — the Catalog spec's Option B hands this exact check to Bookings, §4.1 of that spec).
  4. `PricingRulesService.getActivePricing(serviceId)` — `serviceId` is already confirmed to exist by step 3, so this call cannot itself throw `NotFoundException`; `BadRequestException('Service has no active price')` if it returns `null` (a service that exists but has never had a `PricingRule` created for it, §4.1 of the Catalog spec).
  5. If `teamId` is provided (non-null): `TeamsService.getTeam(teamId)` — `NotFoundException('Team not found')` if `null`. **This existence check is the only team-related invariant this slice enforces** (clarified M3 round 1) — it confirms the referenced `Team` exists, nothing more. Team activity/capacity, availability, or suitability for this booking's `scheduledAt` are not checked, matching §2's explicit deferral of availability/conflict checking; a future capability MUST NOT be inferred as already implied by this existence check passing.
  6. Insert the `BookingEntity` with `status: BookingStatus.PENDING`, `pricingSnapshot: { priceMinorUnits: activePricing.priceMinorUnits }`, and the validated `customerId`/`propertyId`/`serviceId`/`teamId`/`scheduledAt`.
- `UpdateBookingCommand` → `BookingsService.update` — **`customerId`, `propertyId`, and `serviceId` are not fields of `UpdateBookingCommand`/`UpdateBookingInput`/`UpdateBookingDto` at all** — they are immutable after creation (§4.1). Consequently `UpdateBookingInput` is **not** mechanically `PartialType(CreateBookingInput)` as today's code has it (that would make the three immutable FKs merely optional, not absent) — it is its own explicit type carrying only `scheduledAt?`, `status?`, and `teamId?` (nullable — settable to a value, cleared back to `null`, or omitted to retain the current value), plus the existing `id`. `TeamsService.getTeam(teamId)` is re-validated (`NotFoundException('Team not found')`) whenever a non-null `teamId` is supplied. Throws `NotFoundException` if `id` does not exist, matching the existing convention. `pricingSnapshot` is never touched by `update` — reassigning `serviceId` mid-booking is out of scope (§2), so there is no scenario in this slice where re-snapshotting would even apply.
- `BookingsService.findOne`/`.findAll`/`.remove` — unchanged behavior (`findOne` throws `NotFoundException` if missing; `remove` hard-deletes and returns the removed booking, exactly as today). `remove`'s audit event is new (§4.4); its deletion semantics are not — this slice does not convert `remove` into a soft-cancel, since the issue's DoD does not ask for that and `CANCELLED` already exists as a settable `status` value for the soft-cancel case.

### 4.3 RBAC (`@Roles()` matrix — GraphQL only)

Every GraphQL operation gains `AuthGuard`; no operation in this module is public. **This is new** — the pre-migration `bookings` module has no `AuthGuard`/RBAC of any kind, being the only module that predates Admin Foundation.

| Capability | Owner | Ops Manager | Scheduler | Customer Support | Finance | Analyst |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| Create / update / cancel via `status` / delete booking | ✓ | ✓ | ✓ | ✓ | | |
| View booking (get, list) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Rationale: booking intake is the core job of Scheduler and, per the Customers & Properties spec's own precedent, Customer Support (record-facing roles), alongside the two managerial roles every module grants write access to. Read access is broad, matching the Catalog spec's rationale for pricing/catalog data — booking volume and revenue are need-to-know across most of the org (Finance for revenue tracking, Analyst for reporting), the same reasoning, applied here rather than the narrower Cleaners-style view matrix.

### 4.4 Audit logging (GraphQL only)

Every GraphQL mutation logs one `AuditLogger.log()` call, following the existing `AuditLogEvent` contract unchanged. **This is new** for `bookings`, matching every other module's convention:

| Mutation | `action` | `entityType` | `entityId` |
| --- | --- | --- | --- |
| `createBooking` | `booking.create` | `booking` | new `Booking.id` |
| `updateBooking` | `booking.update` | `booking` | `Booking.id` |
| `removeBooking` | `booking.remove` | `booking` | `Booking.id` |

Every successful call — including an `updateBooking` that resubmits already-current values — bumps no separate `updatedAt` field (`Booking` has none today and this slice does not add one; only `createdAt` exists) but still emits its audit event unconditionally, the same "one successful mutation invocation, one audit event" convention every other module follows (Cleaners spec §4.4, reused without re-litigation). Failure semantics are inherited from the Admin Foundation `AuditLogger` contract unchanged: all three mutations MUST persist their audit event within the same transaction as the state change they describe. No audit event is logged for read operations, matching precedent.

**REST exposure posture (made explicit M3 round 1; scope precision added M3 round 2).** **All existing Booking REST endpoints — `GET /bookings`, `GET /bookings/:id`, `POST /bookings`, `PATCH /bookings/:id`, and `DELETE /bookings/:id` alike, reads as well as mutations — remain unauthenticated and unaudited in application code.** This is unchanged from today, not a new gap introduced by this migration (§5); the round-1 wording ("REST mutations are not audited, gain no `AuthGuard`, and gain no `@Roles()`") is superseded by this broader statement so it cannot be misread as implying reads are, or should be, authenticated while only mutations are not. What changes after this migration is that every one of these endpoints now creates, modifies, or returns `Booking` rows carrying real `customerId`/`propertyId`/`serviceId` references instead of fake strings, so this posture is stated here explicitly rather than left implicit: **the legacy REST booking surface is retained solely as this project's original REST-vs-GraphQL comparison artifact and MUST NOT be treated as a production-safe surface — for reads or mutations.** `apps/api` enforces no in-process restriction on any of it (consistent with "no redesign of the REST contract," §5). Deployment/network controls, not this slice's application code, are responsible for preventing untrusted access: if this module is ever deployed anywhere reachable by untrusted clients, keeping the REST routes unreachable to those clients (not publicly exposing them, or gating them at a reverse-proxy/network layer) is an explicit deployment-configuration responsibility outside this specification's scope. This specification does not change that posture — it only converts it from an implicit assumption into a stated one, now scoped to the whole surface rather than mutations alone.

### 4.5 GraphQL operation surface

Queries (names unchanged from today):
- `booking(id: ID!): Booking`
- `bookings: [Booking!]!`

Mutations (names unchanged from today):
- `createBooking(createBookingInput: CreateBookingInput!): Booking!`
- `updateBooking(updateBookingInput: UpdateBookingInput!): Booking!`
- `removeBooking(id: ID!): Booking!`

`CreateBookingInput`: `customerId: ID!`, `propertyId: ID!`, `serviceId: ID!`, `teamId: ID` (nullable), `scheduledAt: DateTime!` (unchanged scalar mapping).

`UpdateBookingInput`: `id: ID!`, `scheduledAt: DateTime`, `status: BookingStatus`, `teamId: ID` (nullable) — see §4.2 for why this is its own explicit shape, not `PartialType(CreateBookingInput)`.

`BookingType` gains four computed fields, all **presentation-layer computed data only** (not fields of the `Booking` domain object, §4.1), the same category as every prior slice's `Cleaner.team`/`Service.activePricing`:
- `customer: Customer!` — backed by `CustomersService.getCustomer(booking.customerId)`. Non-nullable: because no delete operation exists for `Customer` in Phase 1 (§4.1), a `Booking`'s `customerId`, once validated at creation, is guaranteed resolvable for the `Booking`'s entire lifetime.
- `property: Property!` — backed by `PropertiesService.getProperty(booking.propertyId)`. Non-nullable, same reasoning.
- `service: Service!` — backed by `ServicesService.getService(booking.serviceId)`. Non-nullable, same reasoning. Note this resolves the `Service` row as it exists *now*, which may have a different `name`/`durationMinutes`/`active` value than at booking time (§4.1's pricing-only snapshot scope) — that divergence is expected, not a bug.
- `team: Team` (nullable) — backed by `TeamsService.getTeam(booking.teamId)`, returning `null` when `booking.teamId` is `null`, reusing the existing nullable `getTeam` method exactly as the Cleaners spec's `Cleaner.team` does.

`pricingSnapshot: BookingPricingSnapshot!` is exposed as a nested GraphQL object type (`priceMinorUnits: Int!`) — a direct field of `Booking`, not computed (§4.1).

**Resolving these four computed fields over a list MUST NOT issue one query per parent row.** Concretely: `bookings { customer { fullName } property { addressLine1 } service { name } team { name } }` over N bookings MUST NOT issue 4×N separate calls. The implementation MUST introduce or consume a batching-capable read path for each of the four lookups (e.g. `WHERE id IN (...)` bulk queries) — the same N+1 invariant the Cleaners spec §4.5 and the Catalog spec §4.5 both state; no specific mechanism (DataLoader, new plural application-layer methods such as `getCustomers(ids)`, or otherwise) is mandated. **Tightened M3 round 1: calling the existing singular `getCustomer`/`getProperty`/`getService`/`getTeam` contract once per row — including via `Promise.all(bookings.map(b => customersService.getCustomer(b.customerId)))` — is still N calls and does NOT satisfy this invariant, even though it superficially avoids a naive sequential loop.** Whatever mechanism M4 chooses, it must reduce each of the four lookups to a bounded number of calls independent of N. **Clarified M3 round 2, to foreclose a too-literal reading of "consumed by reference"/"consumed as-is" in the dependency table:** the existing singular `getCustomer`/`getProperty`/`getService`/`getTeam` contracts are the authoritative cross-module dependency contracts and MUST NOT be altered or removed to satisfy this invariant, but M4 MAY add new plural, batching-capable read methods to their **owning** modules (`modules/customers`, `modules/catalog`, `modules/cleaners`) — e.g. a `getCustomers(ids)`/`getProperties(ids)` alongside the existing singular methods, mirroring the precedent `PricingRulesService.getActivePricingForServiceIds` and `TeamsService.getTeamsByIds` already set for exactly this purpose. This is additive to those modules' contracts, not a modification of them, and does not require a new specification for the owning module.

`apps/web`'s create-booking flow additionally reuses the Customers & Properties spec's existing `customerProperties(customerId: ID!): [Property!]!` query to populate the property select once a customer is chosen — no new query is added to `modules/customers` for this.

### 4.6 Web UI

- `/app/bookings` — list view (`DataTable`): customer name, property address line, service name, `scheduledAt`, status badge, team name (or "Unassigned"), price (formatted client-side from `pricingSnapshot.priceMinorUnits`, same convention as Catalog's `priceMinorUnits` display). "+ New Booking" opens a `FormDialog`.
- Create flow (`FormDialog`): four `FormField` selects in dependency order — Customer (from `customers`), Property (from `customerProperties(customerId)`, disabled/empty until a customer is chosen), Service (from `services`, filtered client-side to `active: true` — the same responsibility Catalog's spec §4.1 explicitly assigns to this module, exercised here in the UI as well as the application layer's own §4.2 check), Team (from `teams`, optional) — plus `scheduledAt`. Modeled as one dialog with cascading selects, not a multi-step wizard (§2, §5).
- Row click opens a `DetailDrawer` (`?detail=<id>` on `/app/bookings`, per the Dashboard UX Foundation convention) showing all `Booking` fields plus the resolved `customer`/`property`/`service`/`team` names and the snapshotted price; an inline edit form for `scheduledAt`, `status` (select — `CANCELLED` is one of the selectable values here, §3), and `teamId` (select, reassignable). A separate **"Delete booking"** action (relabeled from "Cancel booking" in the initial draft — corrected M3 round 1, §3, §5) opens a `ConfirmDialog` worded as an irreversible, permanent action before calling `removeBooking`; it is presented and styled as destructive (matching `ConfirmDialog`'s existing usage for destructive confirmations elsewhere, Dashboard UX Foundation spec §4.5), visually and terminologically distinct from setting `status: CANCELLED` via the edit form above.
- No middleware change is required: Dashboard UX Foundation's `matcher` (`/app/:path*`) already covers `/app/bookings` (§4.1 of that spec) — the first module to ship after that generalization, and the first to not need its own matcher edit.
- Forms use `FormField` from `packages/ui`; no screen hand-rolls its own inputs.

### 4.7 Validation invariants

- `customerId` MUST reference an existing `Customer` — enforced at the application layer (`NotFoundException`, §4.2). No database FK violation path is expected to surface here in practice since the application check runs first, but the FK constraint (§4.1) remains the database-level authority, per this codebase's standing pattern.
- `propertyId` MUST reference an existing `Property` (`NotFoundException`) **and** that `Property` MUST belong to `customerId` (`BadRequestException`, §4.2) — the second check is new to this codebase (no prior module validates a cross-field parent/child relationship at this depth); `BadRequestException` is used rather than a new module-specific error type, consistent with this codebase's preference for `@nestjs/common`'s standard exceptions over custom domain errors (Cleaners spec §4.7, Catalog spec §4.7).
- `serviceId` MUST reference an existing `Service` (`NotFoundException`) that is `active` (`BadRequestException`) and has an active `PricingRule` (`BadRequestException`) — §4.2.
- `teamId`, when provided, MUST reference an existing `Team` (`NotFoundException`) — §4.2. `null`/omitted is always valid (unassigned).
- `scheduledAt` MUST be a valid date — unchanged `IsDate`/`Type(() => Date)` validation, same as today.
- `NotFoundException`/`ConflictException`/`BadRequestException` (all `@nestjs/common`) are used directly in `BookingsService`, matching every other module's service. This specification does not introduce a module-specific domain error type.

## 5. Rationale

- **REST DTOs' field names — and response bodies — change even though the issue says "preserved as-is"** — this is the single most consequential interpretive decision in this document, made necessary by a genuine tension in the tracking issue's own wording, not a reinterpretation of clear intent. `presentation/rest/booking.controller.ts` and `presentation/graphql/booking.resolver.ts` have always mapped their own transport input into **one shared** `CreateBookingCommand`/`UpdateBookingCommand` (this codebase's README, "Two presentation surfaces, one application layer" — an existing, Accepted architectural rule, not something this slice is free to fork into two parallel commands). The same issue's own DoD requires that shared command be "updated to resolve/validate customer/property/service IDs via their application contracts," and its own scope statement is to "replace today's fake `customerName`/`serviceType` strings with real relations" — unqualified by transport. A REST DTO that kept `customerName: string` would have nothing valid to map into the new command at all. "REST DTOs preserved as-is" is therefore read here as scoped to the REST **surface** — routes, HTTP verbs, status codes, Swagger docs pattern, and (see next point) its pre-existing absence of auth/RBAC/audit — not to literal field names. **This necessarily extends to the response body too (resolved M3 round 1, closing an ambiguity the initial draft left open): this codebase has no separate REST view-model/serializer layer — `BookingController` returns whatever `BookingsService` returns, the same `Booking` domain shape GraphQL exposes.** Once the domain no longer has `customerName`/`serviceType` fields (§4.1), there is nothing left for a REST response to reconstruct them from; a `GET /bookings/:id` response after this migration returns `customerId`/`propertyId`/`serviceId`/`teamId`/`pricingSnapshot`, not the old field names under any guise. "Response shape preserved" means the response envelope (a single JSON object per booking, HTTP status codes, error format) is unchanged — not that the specific fields inside it are frozen. Flagged explicitly for M3 confirmation, since the alternative reading (forking the command in two so REST can keep serving the old fake shape) is a materially larger and architecturally regressive change nothing else in the issue or Phase 1 Design supports.
- **REST gains no `AuthGuard`, RBAC, or audit** — unlike the DTO field-name question above, this is a deliberate, not a forced, decision. The REST surface already has zero authentication or audit today (it predates Admin Foundation entirely) and Phase 1 Design §7 states "no redesign of the existing Booking REST contract — it's preserved as a reference implementation." Adding cross-cutting security/audit infrastructure to it would be exactly that kind of redesign, and nothing in the issue's DoD asks for it. The GraphQL surface, by contrast, gaining RBAC/audit is not a redesign — it is this module catching up to the parity every other module has had since its own first specification, which the issue's dependency on M2–M5 (Phase 1 Design §4) already implies. **This asymmetry is now stated as an explicit exposure posture, not left as an implicit consequence of the design (added M3 round 1, §4.4):** the REST surface remaining unauthenticated is not new behavior this migration introduces, but the migration does change what an unauthenticated caller can now read/write — real customer/property/service references instead of fake strings — which is exactly why leaving the posture implicit was a real gap, independent of whether the underlying decision (no REST auth) itself changes.
- **Delete/Cancel terminology corrected (M3 round 1)** — the initial draft's web UI labeled the destructive `removeBooking` hard-delete as "Cancel booking," while the domain model separately (and correctly) supports a non-destructive `status: CANCELLED` transition via `updateBooking`. Presenting both under the word "cancel" would let a user reasonably believe a "cancelled" booking remains historically available, when `removeBooking` actually erases it permanently. The fix is UI wording only, not an API redesign: `removeBooking`'s hard-delete semantics, its audit action name (`booking.remove`), and REST's `DELETE /bookings/:id` are all unchanged (§4.2, §4.4, §7) — only the web label and its `ConfirmDialog` copy change to unambiguously destructive language ("Delete booking"), and §3 now defines Cancel and Delete as the two distinct operations they are. Redesigning the API so "cancel" in the UI maps to `updateBooking(status: CANCELLED)` was considered and declined for this round, since the issue's DoD does not ask for an API change and the terminology fix alone resolves the actual defect (a labeling/comprehension risk, not a missing capability).
- **`teamId` is a plain field of `Create`/`UpdateBookingInput`, not a separate `assignBookingTeam` mutation** — a deliberate divergence from the Cleaners spec's `assignCleanerToTeam` precedent. That precedent exists because a `Cleaner`'s team membership is a distinct, independently auditable HR event from the cleaner's own creation (Cleaners spec §5). A booking's team is not comparable: the issue's own DoD describes team selection as one step in a single "customer → property → service → team" intake walk, not a separate later workflow, and reassigning a booking's team later is closer in kind to rescheduling it (`scheduledAt`) than to a workforce-management decision. Introducing a second mutation here would add API surface the issue does not ask for, for a distinction (creation vs. assignment) that does not carry the same weight in this module that it does in Cleaners.
- **Pricing snapshot scoped to price only** — see §4.1's inline rationale. Snapshotting more (e.g. `Service.name` at booking time) is a plausible future need but is not what "must not retroactively alter what a historical booking appears to have cost" (Phase 1 Design §2.3) actually asks for; adding it now would be scope this specification was not asked to carry.
- **A TypeORM embedded column for `pricingSnapshot`, the first in this codebase** — chosen over a flat `priceMinorUnitsAtBooking` column for one direct reason (simplified M3 round 1, dropping the initial draft's more speculative "leaves room to grow" framing): the domain contract (§4.1) explicitly defines the pricing snapshot as a value object, and a TypeORM embedded column is this framework's existing mechanism for persisting exactly that shape without promoting it to an independent entity/table. Flagged for M3 rather than treated as an obvious default, since it is new to this codebase; the generated column name is an M4 verification item, not a design decision (§4.1).
- **No backfill strategy for existing `bookings` rows** — the initial draft omitted this entirely, which the M3 round 1 review correctly identified as a blocker: a migration description that never states whether production data must survive leaves M4 to invent that answer, which is exactly the kind of normative gap M3 exists to catch. §4.1's Legacy data migration note resolves it by stating, as fact, that Phase 1 has no production deployment and every existing row is deterministic seed data — so the migration may replace the legacy columns directly. This is a factual claim about this project's current state (verifiable against `booking.seed-data.ts` and the absence of any Phase 1 deployment), not a policy this specification is asserting should hold indefinitely.
- **Cascading `propertyId`-belongs-to-`customerId` check, new to this codebase** — no prior module has validated a parent/child relationship this way (Property's own creation only validates its direct parent, `customerId`, exists — it has no grandparent to check). This slice needs it because `Booking` references both `customerId` and `propertyId` independently; without the check, a client could submit a mismatched pair and produce a `Booking` that silently references an unrelated customer/property combination.
- **No availability/conflict checking** — the issue's DoD does not ask for double-booking prevention, and inventing that business rule here (what counts as a conflict? per team? per time slot? per property?) is a real product decision this specification is not positioned to make unilaterally. Deferred explicitly, not silently.
- **No REST surface changes beyond DTO field names** — consistent with the "preserved as-is" reading above: this module's REST controller, tests, and status model stay the reference implementation the Phase 1 Design's non-goals describe, not a second product surface kept in lockstep with GraphQL going forward.

## 6. Acceptance criteria (for this specification)

- The domain object shape (`customerId`/`propertyId`/`serviceId`/`teamId`/`pricingSnapshot`), the application-layer validation chain and its exact exception types (§4.2, §4.7), and the RBAC/audit additions to the GraphQL surface (§4.3, §4.4) are confirmed correct against the project owner's intent.
- **The REST-DTOs-field-name-and-response-body interpretation (§5, first bullet) is explicitly confirmed, not silently accepted** — this is the specification's central judgment call, made necessary by a real tension in the tracking issue's own wording, and the alternative reading (forking the shared command so REST keeps the old fake fields) must be explicitly rejected or this document returned for revision.
- The decision that REST gains no `AuthGuard`/RBAC/audit, while GraphQL does, is explicitly confirmed as intentional asymmetry, not an oversight — including the explicit "not a production-safe mutation surface" exposure statement (§4.4) as the correct way to state that asymmetry, rather than requiring REST to gain authentication in this slice.
- **The Legacy data migration note (§4.1 addendum) — that no backfill is required because Phase 1 has no production deployment and existing rows are exclusively deterministic seed data — is confirmed as factually accurate**, not merely a convenient assumption; if this is wrong (some environment's `bookings` data must actually survive), the document must be returned for a real backfill strategy (§5).
- **The Cancel/Delete terminology correction (§3, §4.6, §5) is confirmed as sufficient** — a UI wording and `ConfirmDialog` framing fix, with `removeBooking`'s hard-delete API semantics and `booking.remove` audit action name explicitly left unchanged, not redesigned into a soft-cancel.
- The `teamId`-as-a-plain-field decision (declining the Cleaners `assignCleanerToTeam` precedent) is confirmed, including its rationale (§5).
- The pricing-snapshot scope (price only, embedded column, resolved at creation time not `scheduledAt`) and the new `propertyId`-belongs-to-`customerId` cross-field check are confirmed.
- **(Added M3 round 2) Pricing snapshot immutability — the specific invariant this migration exists to guarantee (§1) — MUST be covered by a dedicated integration/e2e test that changes a service's active pricing after booking creation and confirms the existing booking's `pricingSnapshot.priceMinorUnits` is unchanged (§2); this is a distinct test from the create-booking golden path, not satisfied by it. Immutability of `customerId`/`propertyId`/`serviceId` after creation, and the full mutable range of `teamId` (assign, reassign, clear to `null`), MUST also be asserted, not merely documented (§2).**
- The GraphQL N+1 batching invariant's tightened wording (§4.5) — that a per-row `Promise.all` over the existing singular `getX()` contracts does not satisfy the invariant — is confirmed as the correct bar for M4, without this specification mandating a specific mechanism.
- No open contradiction with the Accepted Phase 1 Design, Admin Foundation, Customers & Properties, Cleaners & Teams, Catalog, or Dashboard UX Foundation specifications.
- Scope boundaries (§2) are explicit enough that M4 Implementation Planning does not need to make further scope decisions.

## 7. Non-goals

- Redesigning any Admin Foundation, Customers & Properties, Cleaners & Teams, Catalog, or Dashboard UX Foundation contract — all consumed or reused as-is.
- Any `modules/jobs` or `modules/quality` change or booking-to-job linkage — M7/M8's concern per Phase 1 Design §4 dependency order.
- Availability/conflict checking, re-snapshotting, a dedicated team-assignment mutation, a multi-step wizard UI, cascading-delete behavior, and currency/multi-currency support — all explicitly deferred or declined per §2/§5.
- Converting REST's hard-delete `removeBooking`/`DELETE /bookings/:id` into a soft-cancel, or adding `AuthGuard`/RBAC/audit to REST — explicitly declined per §5.
