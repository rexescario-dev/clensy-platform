# @clensy/web

Reusable Clensy domain components — the sole home for components representing Clensy business concepts, positioned between `@clensy/ui` (generic UI primitives and composition) and `apps/web` (application-level page and component composition). See [the design spec](../../docs/superpowers/specs/2026-09-19-clensy-web-login-form-design.md) §1 and §4.1 for the full architecture and rationale.

**Boundary this package enforces:**

- Domain components (components representing a Clensy business concept) live here, grouped by domain (e.g. auth/, bookings/, staff/).
- This package must not import shadcn, radix-ui, or apps/web/components/ui directly — UI primitives come only through @clensy/ui.
- This package must not import @clensy/client, @apollo/client, or any other GraphQL/network client — host applications inject data actions (e.g. LoginForm's onLogin) instead.
- This package must not import next-intl — framework/application i18n integration stays in apps/web.
- This package must not import from apps/web.

**Formerly a known, intentional inconsistency — now reconciled:** `LoginForm` and `BookingDataTable` both fully self-translate: neither takes a caller-supplied string prop for its UI copy, both own their entire string surface via their own default `en` message catalog under `src/i18n/` and `useClensyTranslations`. The only string either component accepts from a caller is an optional `errorMessage` override, falling back to a package-owned translated default (`resolveMessage(override, t('error'))`) when omitted — apps/web may layer partial overrides on top through `ClensyI18nProvider`, deep-merged with the package defaults, but doesn't have to. See [the reusable-data-table design addendum](../../docs/superpowers/specs/2026-09-19-reusable-data-table-design.md) for `BookingDataTable`'s original self-translating design, [the errorMessage normalization spec](../../docs/superpowers/specs/2026-09-20-component-error-message-api-design.md) for how the two components' error props were aligned, and [the LoginForm self-translating spec](../../docs/superpowers/specs/2026-09-20-login-form-self-translating-design.md) for how `LoginForm`'s remaining `labels` prop was retired to close this gap.

## LoginForm

`auth/LoginForm` is a client-side login form component that validates input, presents server-error feedback, and calls a host-provided `onLogin` callback to perform authentication. It takes no UI-copy props at all — title, field labels, and button text all resolve from `useClensyTranslations('auth')` — and an optional `errorMessage?: string` override for mutation failures — when omitted, `LoginForm` displays its own translated default (`"Invalid email or password."`) rather than requiring the host to supply one — see [the LoginForm self-translating spec](../../docs/superpowers/specs/2026-09-20-login-form-self-translating-design.md) §4.1 for the full contract, [the errorMessage normalization spec](../../docs/superpowers/specs/2026-09-20-component-error-message-api-design.md) §4.2 for the error-default mechanism this builds on, and [the original design spec](../../docs/superpowers/specs/2026-09-19-clensy-web-login-form-design.md) §4.4/§5 for the `onLogin` resolve/reject error-handling rationale.

## BookingDataTable

`bookings/BookingDataTable` owns Bookings' domain-specific table columns (Customer, Property, Service, Scheduled, Status, Team, Price) and rendering, delegating generic table behavior (pagination, and — unused by Bookings today — sorting and selection) to `@clensy/ui`'s `DataTable`. It takes plain booking values, a host-injected `formatPrice` callback (price formatting lives in `apps/web`, which this package must not import from), and pagination props — see [the design spec](../../docs/superpowers/specs/2026-09-19-reusable-data-table-design.md) §4.4 for the full contract, including why `Booking`'s shape is a structural pass-through of the host's GraphQL result rather than an explicit view model.

Column headers and generic strings (`Unassigned`, `No bookings.`) come from `useClensyTranslations('bookings')`, not props — the component is fully functional with zero application-level integration, using its own `src/i18n/messages/en/bookings.ts` defaults. Error display uses two separate props, not one: `hasError?: boolean` is the occurrence signal (the host — e.g. a failed GraphQL query — is the only thing that knows whether an error actually happened), and `errorMessage?: string` is text-only, resolved (`errorMessage || t('error')`) only when `hasError` is `true`; omitting `errorMessage` — or passing an explicit empty string — while `hasError` is `true` both fall back to the translated default (`"Unable to load bookings."`), because the underlying `@clensy/ui` `DataTable.error` prop this feeds is itself truthy-gated and can never display an empty string as an error state; omitting `errorMessage` while `hasError` is `false` never shows an error at all — see [the errorMessage normalization spec](../../docs/superpowers/specs/2026-09-20-component-error-message-api-design.md) §4.3/§6 for why a single string prop can't carry both meanings once it owns a default, and its Post-Accept correction for why this component uses `||` rather than `LoginForm`'s `??`.

## Staff console (`staff/`)

`staff/StaffDataTable` and `staff/CreateStaffForm` are the staff-administration domain components for a Tenant Owner's own tenant ([multi-tenant spec](../../docs/superpowers/specs/2026-09-23-multi-tenant-architecture-design.md) §4.3/§4.8; [#88 plan](../../docs/superpowers/plans/2026-10-01-tenant-staff-administration-ui-plan.md)). Both are presentation-only: `apps/web/app/app/admin/page.tsx` owns the queries, mutations, dialogs and the session redirect.

- `StaffDataTable` renders email, a role label from the shared `roles` namespace (Tenant Owner as a `secondary` badge, operational Staff roles as plain text), and Active/Disabled status. **Disable** is offered only for active rows that are not `currentAdminId` — the API rejects self-disable; hiding it is UX, not authorization. A role outside the tenant role set renders as its raw identifier.
- `CreateStaffForm` renders the email/password/role fields inside the host's `FormDialog`. The role `<select>` groups `STAFF_ROLE_GROUPS` under **Tenant Owner** and **Staff**, with option labels from the shared `roles` namespace; `SUPER_ADMIN` is never offered. A hint appears when Tenant Owner is selected. An optional `errorKey` renders the translated error as an alert.
- `STAFF_ROLE_OPTIONS` / `STAFF_ROLE_GROUPS` hold stable role identifiers (`StaffRole`), never display strings; `isStaffRole` narrows a role string. `StaffRole` is declared here rather than imported from `@clensy/client` (see the boundary above).
- `STAFF_ERROR_KEYS` / `StaffErrorKey` are the typed failure keys the host maps API errors to (`apps/web/lib/staff-console.ts`, by operation + HTTP status); the `staff` namespace's `errors.<key>` owns the text, so no English crosses the package boundary.

## Roles (`roles/`)

`roles/admin-roles.ts` is the shared role identity for every `AdminUser` role ([multi-tenant spec](../../docs/superpowers/specs/2026-09-23-multi-tenant-architecture-design.md) §4.3; [#89 plan](../../docs/superpowers/plans/2026-10-01-tenant-aware-application-shell-plan.md) decisions 7–8): `AdminRole` (the six `StaffRole`s plus `SUPER_ADMIN`, declared locally, not imported from `@clensy/client`), `ADMIN_ROLES`, `isAdminRole`, and `ROLE_INITIALS`. The initials are fixed per role (e.g. `AN`, `SA`, `TO`) and never derived from a translated label. Labels for all seven roles live only in the `roles` i18n namespace, read by the staff components and by the apps/web shell user menu. One app-level `roles` override through `ClensyI18nProvider` therefore changes a label wherever it is read.

## Laundry presentation (`laundry/`)

Shared presentation helpers for the laundry screens of [#154](https://github.com/rexescario-dev/clensy-platform/issues/154) ([laundry lifecycle spec](../../docs/superpowers/specs/2026-09-06-laundry-orders-lifecycle-design.md) §4.3, §4.4, §4.9 and Amendment #164 §8.4.4; [#157 plan](../../docs/superpowers/plans/2026-10-10-laundry-ui-foundation-plan.md)). The `/app/laundry` list uses them ([#163](https://github.com/rexescario-dev/clensy-platform/issues/163), [#163 plan](../../docs/superpowers/plans/2026-10-10-laundry-order-list-plan.md)), as does its intake dialog ([#160](https://github.com/rexescario-dev/clensy-platform/issues/160), [#160 plan](../../docs/superpowers/plans/2026-10-13-laundry-intake-modal-plan.md)) and the order page `/app/laundry/[id]` ([#156](https://github.com/rexescario-dev/clensy-platform/issues/156), [#156 plan](../../docs/superpowers/plans/2026-10-14-laundry-order-page-plan.md); its Weighing editor is [#155](https://github.com/rexescario-dev/clensy-platform/issues/155), [#155 plan](../../docs/superpowers/plans/2026-10-14-multi-entry-laundry-weighing-plan.md)), and its Services editor ([#158](https://github.com/rexescario-dev/clensy-platform/issues/158), [#158 plan](../../docs/superpowers/plans/2026-10-15-laundry-services-selection-plan.md)), which uses `LAUNDRY_STATUS_TONE`, `<LaundryOrderProgress>`, `<LaundrySearchCombobox>`, `formatWeightGrams` and `laundryOrderActions`; the remaining #154 screens adopt them in later slices.

- `LaundryOrderStatus` and `LaundryFulfillmentType` are declared locally, not imported from `@clensy/client`. `apps/web/lib/laundry-presentation-contract.test.ts` pins them to the generated client types under `tsc`. `LAUNDRY_STATUS_TONE` is the spec §4.9 badge-tone map, and `LAUNDRY_ORDER_STATUSES` lists every status.
- `formatWeightGrams(grams)` renders integer grams as kilograms using integer arithmetic only: two decimals, or three when the gram digit is non-zero (`1` → `0.001 kg`, `2500` → `2.50 kg`). Negative, fractional or unsafe input throws `RangeError`. Money stays `formatMinorUnits` in apps/web.
- `laundryOrderActions(status, fulfillmentType, role)` returns the verbs a screen may show, in presentation order. It is the intersection of the spec §4.3 matrix (plus re-weighing a `WEIGHED` order), the fulfillment branch, and the API's role sets. `canReceiveLaundryOrder(role)` covers intake. `ANALYST`, `SUPER_ADMIN` and a still-loading role get nothing. `LAUNDRY_DESTRUCTIVE_VERBS` marks the verbs that need a confirmation. The helper is presentation only, and the API decides. If the API's matrix or role sets change, re-run the plan's Task 4 reconciliation script.
- `laundryProgressSteps(status, fulfillmentType)` is pure, in a module without `'use client'`. It returns the happy-path steps, or `null` for a terminal exception. `<LaundryOrderProgress>` renders those steps as an ordered list with `aria-current="step"` on the current step only, or a terminal exception as a badge plus one sentence. `AWAITING_PAYMENT` takes the Paid slot only while it is the status. `COMPLETED` marks every step done.
- `<LaundryOrderDataTable>` (#163) is the list's presentation:
  - **Columns:** customer, short order id (the full id in `title` and screen-reader text), fulfillment, status badge, weight, total and created.
  - **Toolbar:** a labelled search field and native status and fulfillment selects, plus a "Clear search and filters" button while any is active.
  - **Mobile:** a card per order below `sm`.
  - **States:** the plain or filtered empty copy.

  Like `BookingDataTable`, it delegates to `@clensy/ui`'s `DataTable`, takes a host-injected `formatPrice`, and is props-driven. The host owns the URL state and the query.
- `laundry-order-sort.ts` is the list's sort contract:
  - **Keys:** `LAUNDRY_ORDER_SORT_KEYS` lists the `LaundryOrderSortFields`. The table offers Order, Fulfillment, Status and Created. Customer is not sortable, because the server's only customer sort is `customerId`, which is not alphabetical.
  - **Clicks:** `clickedLaundrySortKey` takes only the clicked column from `DataTable` and rejects unknown keys and directions. `nextLaundryOrderSort` applies the list's own transitions: a new column sorts ascending; ascending goes to descending; descending goes to `null`, which means "restore `DEFAULT_LAUNDRY_ORDER_SORT`" (Created, descending). Created itself toggles ascending ↔ descending.
- `<LaundrySearchCombobox>` ([#158](https://github.com/rexescario-dev/clensy-platform/issues/158)) is the shared WAI-ARIA editable combobox, built from a native input (`@clensy/ui` has no Combobox) and extracted from the customer picker:
  - **Props:** `copy` (`label`, `empty`, `error`, `searching`, `more`), `renderOption`, `openOnFocus`, `onFocus`, `onBlur`, `disabled` and `truncated`, plus `id`, `error`, `inputRef`, `options` (each with an `id`), `query`, `status` and the `onQueryChange` / `onSelect` callbacks. With `openOnFocus` the list opens on focus and stays open for an empty text, as the services editor's catalog pickers do; without it the list opens only for a non-empty text, as in the customer picker.
  - **Ownership:** the host owns the text, the server search, the `status` (`idle` / `loading` / `error` / `ready`), the options and the selection. The combobox owns only whether the list is open and which option is active.
  - **Selection contract:** `onQueryChange` fires only for a user edit, and the host clears its selection there. On `onSelect` the host sets the text to the chosen name itself, so a selection is never cleared by its own display text.
  - **Active option:** tracked by option id, never by position. Options render only for a `ready` search. A stored id that no longer names a rendered option is dropped, so `aria-activedescendant` only ever names a rendered option, and nothing from an older search can be chosen.
  - **Keyboard:** ArrowUp/ArrowDown wrap, Enter selects while the list is open (it never submits the form), and Escape closes an open list. Escape stops with `nativeEvent.stopImmediatePropagation()`, because Next.js hydrates React on `document`, the same node as `Modal`'s Escape listener; with the list closed, Escape reaches the `Modal`.
  - **Rows and lines:** the caller's `renderOption` draws each row. Inline `searching`, `empty` and `error` lines show for their states and, when `truncated`, the `more` line.
  - **Announcements** ([#181](https://github.com/rexescario-dev/clensy-platform/issues/181), [plan](../../docs/superpowers/plans/2026-10-16-intake-screen-reader-polish-plan.md)):
    - **Region:** one visually hidden `role="status"` region (`<id>-status`) is always mounted outside the popup and announces those messages politely. The inline lines carry no live role, so nothing is read twice.
    - **When it holds a message:** only while the list is open. It is empty when the list is closed (Escape, blur, selection, a cleared text, `idle`).
    - **Which message:** if a page is both empty and `truncated`, the popup shows both lines but the region announces only `empty`.
- `<LaundryCustomerPicker>` (#160) is the intake dialog's customer search, now a thin wrapper over `<LaundrySearchCombobox>` with unchanged behaviour. It supplies the `create.customer.*` copy and the row text: `fullName`, with `phone`, or `email` when `phone` is empty, as secondary text. Its inline lines read "Searching…", "No customers match.", "Unable to search customers." and, when `truncated`, "More customers match…".
- `<LaundryFulfillmentFieldset>` (#160) renders pickup and delivery as two native radios in a `fieldset`, each with its description, under "This choice is fixed at intake." Each radio is named by its title alone (`aria-labelledby`) and described by its description, so the description is read once. An optional `error` shows under the rows, marks both radios `aria-invalid` and is appended to each radio's `aria-describedby`; the `fieldset` stays described by the helper only. An optional `inputRef` goes on the checked radio, so a form can focus it ([#181](https://github.com/rexescario-dev/clensy-platform/issues/181)).
- Copy comes from the `laundry` namespace. Enum-valued maps are keyed by the GraphQL value (`status`, `fulfillment`, `invoicePaymentStatus`, `paymentTerms`, `progress.terminal`). Verb maps are keyed by `LaundryOrderVerb`: `actions` (labels), `success` (toast text), `failure` (inline errors) and `confirm` (exactly the destructive verbs). The list's copy is under `list` (columns, filters, search label, title, create button, filtered-empty text). The intake dialog's copy is under `create` (title, submit and submitting labels, `customer.*` search lines and required message, `fulfillment.*` legend, helper and descriptions, success, failure and the "may have been created" message); its fulfillment labels reuse `fulfillment`. The order page's copy is under `order` (back link, `summary.*` terms, `sections.*` headings and `sectionsLabel`, the read-only facts under `invoice` and `actions`, `overview.*` (the no-lines sentence and the priced-count pointer to Price, `seePrice`), the Price card copy under `price.*` (#162: the `estimate` and `final` eyebrows, the `noBase`, `incomplete`, `loading` and `failed` sentences, `retry`, `confirm` and `confirming`, the `caption`, `estimatedTotal` and `total`, rate phrases under `rate.*` with a `{price}` placeholder, `items` with an `{n}` placeholder and `itemsOne`, `minimumApplied` and `minimumAppliedAmount` with an `{amount}` placeholder, `more`, the `beforePricing` and `notPriced` sentences, and the Confirm `success` toast and `failure` fallback), the Services copy under `services.*` (base and add-on labels with an `{n}` placeholder, the add, remove and count labels, `search.*` lines per kind plus the shared searching and "first 20" lines, `error.*` messages, `duplicate`, `noPrice` with a `{name}` placeholder and `noPriceRow`, `previewFailure`, and the `locked`, `beforeWeigh` and `none` sentences), and the Weighing editor's labels, row copy (`bag` and `remove`, with a `{n}` placeholder), validation messages under `error.*`, the locked sentence, toast and failure text under `weighing`); it reuses `status`, `fulfillment`, `actions`, `invoicePaymentStatus`, `error.order` and `noActions`.

## i18n (`src/i18n/`)

`@clensy/web` owns default `en` messages for its components — `BookingDataTable`, `LoginForm` and the staff components each resolve their entire display-string surface this way, not just their error text (see above). `getDefaultMessages()` assembles the flat, namespace-keyed catalog (mirrors `apps/web/i18n/messages.ts`'s own `getMessages()` convention) from `auth`, `bookings`, `laundry`, `roles` and `staff` namespaces today. The `staff` namespace also carries the staff admin page's own copy; role labels live only in `roles` (#89 consolidated them and retired `apps/web/lib/role-presentation.ts`). `resolveMessage(override, fallback)` (`src/i18n/resolve-message.ts`, `override ?? fallback`) resolves `LoginForm`'s `errorMessage`, honoring an explicit empty-string override as real (rendered as a blank alert) since `LoginForm` owns its own render gate. `BookingDataTable` does **not** use `resolveMessage` — it resolves via `errorMessage || t('error')` directly, because its `errorMessage` feeds `@clensy/ui`'s `DataTable.error`, a truthy-gated prop that can never display an empty override as an error state; an empty override there falls back to the default instead. `ClensyI18nProvider` (optional — components work with no Provider in the tree at all) takes a plain `locale` string and an optional `overrides` object, deep-merged onto the package defaults via `deepMerge` — never a shallow spread, so overriding one leaf never drops its siblings. `deepMerge` is also exported from the package entry (#118), so apps/web composes its static and tenant override layers with these exact semantics. `useClensyTranslations(namespace)` returns a `t(key)` function scoped to that namespace. This package has no next-intl dependency; the host application (apps/web) is responsible for resolving its own real locale (via its own next-intl setup) and passing it to `ClensyI18nProvider` as a plain string.
